# 模块设计：Memory 块级标脏与分级序列化缓存

| 项目 | 内容 |
| --- | --- |
| 源码 | `src/kernel/memory/`（未实现） |
| 所属架构章节 | 架构设计 6.2 标脏与序列化 |
| 成熟度 | 候选（由数据触发实施） |
| 日期 | 2026-10-16 |

本文档描述 Memory 序列化的进阶实现。v1（架构设计 6.2）以"存储单元"为标脏和序列化单位；当实测数据表明单元级序列化成本过高时，按本文档把单元内部再切分为块，并增加分级缓存。对外接口（长路径读写、实体空间、版本迁移）保持不变。

## 1. 触发条件

满足任一条件时实施：

| 条件 | 默认阈值 |
| --- | --- |
| 主 Memory 文本总长度 | 超过 `MEM_CHUNK_TRIGGER`（300 KB） |
| commit 阶段序列化 CPU 的 7 日均值 | 超过本 tick 预算的 5% |
| 单个分区的平均脏写频率与体积之积 | 进入统计前 5% 且体积超过 20 KB |

## 2. 块深度

- 申请分区时可声明 `chunkDepth`，取值 0、1、2。0 表示整个分区一个块（与 v1 相同）；1 表示每个顶层键一个块；2 表示每个二级键一个块，适合"房间 → 记录"这类两级 Record。默认值为 0，只有被触发条件选中的分区才改为 1 或 2。
- 写入路径的前 `chunkDepth` 段决定被标脏的块。路径比块深度短时（替换整个父容器），该前缀下的全部块都被标脏。
- 新增或删除块会让所属单元的键清单变脏，该单元的拼接结果需要重建。

## 3. 分级序列化缓存

```text
块串（JSON.stringify(块值)）
  → 单元串（'{' + 各 '"键":块串' 以逗号相连 + '}'）
    → 命名空间串（同理拼接各单元串）
      → 根串 → RawMemory.set
```

- commit 时只对脏块执行 `JSON.stringify`；只重拼含有脏块或结构变化的单元；只重拼含有变化单元的命名空间；根串拼接一次。
- 每级缓存记录字符串长度，体积统计在 O(1) 时间内取得。

## 4. 成本分析

| 环节 | 成本 | 说明 |
| --- | --- | --- |
| 序列化 | 与脏块总大小成正比 | 块越细越省 |
| 单元重拼 | 与该单元的块数成正比 | 块越细越多 |
| 命名空间与根拼接 | 与变化单元数和总长度成正比 | 每 tick 至多一次 |
| `RawMemory.set` | 与总长度成正比 | 平台行为，无法避免 |

块的粒度不超过二级：再细的块会让键字符串和拼接开销超过节省的序列化成本。

## 5. 提交与恢复

- 提交顺序不变：拼接根串 → `RawMemory.set` → 更新各级缓存基线 → 清空脏集合。任一步被中断，脏集合保留，下一 tick 重新提交。
- global reset 后各级缓存为空，第一次提交完整编码一次，此后进入增量模式。

## 6. 验证

- **等价性测试**：随机生成数据与写入序列，断言增量拼接得到的文本与对完整对象 `JSON.stringify` 的结果完全一致；覆盖块的增删、路径短于块深度的写入、被中断的提交。
- **收益验证**：在实施前后对比 commit 阶段的序列化 CPU，收益不足时回退为 v1。
