# MemoryManager 设计方案

交付状态：**已交付**（契约、存储格式、生命周期恢复及 §10 验收项；逐项标记见 §10）。目标环境性能验收阈值待定。可调用能力见 [使用说明](../../usage/core/memoryManager.md)。

## 1. 定位与目标

`core/memoryManager` 为每个模块提供独立的逻辑持久化分区，以分区为 `JSON.stringify()` 和字符串缓存的单位。模块通过显式 `commit` 或 `remove` 声明修改；收尾只重新序列化需要提交的分区，复用其他分区的 JSON 片段，拼接完整文本后交给 RawMemory。

深路径读写是同等重要的公共能力，用于简化嵌套数据访问、完整子对象赋值和类型检查；路径深度不决定序列化粒度。一个深层字段变化仍使整个所属分区变脏，不维护字段级 JSON 片段。

所有分区共享主存储容量，逻辑隔离不表示各自拥有独立的物理容量或独立写盘事务。模块不接触全局 Memory、RawMemory 或其他持久化旁路。平台读写仅位于本模块的适配层。

运行模型只使用主 RawMemory，不提供 Segment 存储、分配、激活或搬迁能力。访问器没有 pending、ready、recovery 等可用性状态，也没有 `access()` 或 `status()`。

## 2. 装配与同步生命周期

Runtime 是唯一组合根，显式注入 Logger 和平台端口，创建每个 global 唯一的 MemoryManager。判定真实 tick 的来源由 Runtime 的共享 getGame 端口派生，与 Framework 调用 begin/end 所用的 tick 同源。Framework 只消费 `src/contracts/memory.ts` 的宿主协议，不导入或创建存储实现。

宿主端口包括 `bind(owner)`、`begin(tick)`、`end(tick)` 和 `getStatus()`。创建工厂和绑定 owner 只操作 heap，不读取存储。

1. 首次 `begin(tick)` 同步读取并解析主文本，校验命名空间，建立分区记录和已提交片段基线；全部成功才发布装载结果。
2. 模块在成功的 `begin` 之后，通过 `context.memory(localId, options)` 同步申请分区。初始化或数据版本迁移完成后才返回访问器。
3. 访问器在所属管理器的 global 生命周期内有效，后续 tick 可直接读写。每个方法间接访问所属分区，不捕获一个按 tick 失效的视图。
4. 所有插件收尾后由 Framework 调用 `end(tick)`，提交全部脏分区。
5. global reset 后 heap、访问器、脏集合和片段缓存全部重建，只恢复平台保存的文本。

`begin` 必须先于插件 setup 和业务钩子执行。申请没有集中收集窗口，迟到申请与普通申请遵循同一规则。宿主必须按 tick 递增、先 begin 后 end 调用；重复 begin/end 同一 tick 不重复装载或提交，嵌套生命周期调用拒绝。访问器跨 tick 有效，但修改只允许在 begin/end 之间；本 tick 收尾后的写入属于调用协议错误。

### 2.1 跨 tick 中断恢复

宿主在真实的新 tick 顶层调用 begin；同一执行栈内的回调不得通过传入更大的 tick 绕过重入保护。生命周期与分区修改的临时锁必须带 tick 归属，不得使用无法区分历史中断的永久布尔锁。相同 tick 的重复 begin 不重新开放已结束的写入阶段；未 begin 的 end、倒退 tick 及同步重入均拒绝。

若 heap 保留而上个 tick 未正常 end，更大 tick 的 begin 终结旧阶段、清除旧 tick 临时锁并打开新阶段。已经发布的工作对象、访问器、脏集合和结构变化继续保留；不补跑旧业务回调、不回滚回调的部分修改。未完成的初始化或迁移候选不发布，下一次申请可重试；首次装载若被硬终止且没有发布结果或记录明确的装载错误，下一次 begin 可重新装载。

提交严格按“平台接受完整文本 → 更新全部候选基线 → 清理脏集合及结构变化标记”的顺序执行。基线全部更新之前不得逐分区清脏；脏集合是待提交工作的唯一索引，不另设提交批次恢复结构。编码、平台调用或基线更新中断时，全部脏分区自然保留，下次 begin 丢弃遗留候选，end 按最新工作对象重试。平台可能已经接受文本，因此重复写入是允许的。若中断发生在最终清理阶段，所有候选基线已经更新，已清理项安全，残留项仅导致冗余提交。正常 clean tick 不扫描分区。

global reset 后只从实际持久文本重建，不恢复 heap 的未提交修改或临时锁。该协议处理生命周期恢复，不承诺 CPU 硬终止时业务修改的原子性。

## 3. 身份、申请与版本

分区身份是稳定二元组 `(owner, localId)`。Framework 为插件上下文绑定 pluginId，Runtime 为普通模块绑定模块名；调用方只提供显式 localId。身份不能采用随机数、注册顺序或构建 hash。owner/localId 必须是非空合法字符串，拒绝原型相关保留键；内部索引采用 Map 或 null 原型对象。

申请配置为：

| 字段 | 约束 |
| --- | --- |
| `version` | 正整数，表示模块 payload 的版本 |
| `initialize()` | 同步返回首次安装的分区对象 |
| `migrate(data, fromVersion)` | 可选；同步校验未知旧数据并返回目标版本对象 |

所有分区采用统一提交时机：在本 tick 的 end 提交全部脏分区。申请配置不提供提交层级、提交间隔或存储分配优先级；Framework 的执行优先级不改变持久化提交规则。

initialize 与 migrate 必须是只依赖输入的确定性函数：不读取 Game、服务或其他分区，依赖游戏状态的数据在申请成功后通过修改 API 补齐。只有确认不存在历史分区时才执行 initialize。已存储版本与申请版本不同，必须执行显式 migrate；包含未知旧版本或降级情形，不能偷偷初始化为空。迁移失败保留历史数据，申请抛错，不发布访问器。迁移处理的是与原记录隔离的数据副本，回调抛错不能污染持久基线或其他分区。initialize 与 migrate 的返回值在校验后复制为工作对象，调用方返回模块级常量或共用对象不会让分区之间、分区与常量之间共享可变数据。

相同身份、相同声明重复申请返回同一访问器。重复声明按规范化后的 version 和 initialize/migrate 函数引用检查；回调应使用稳定引用，不比较函数源码。配置冲突抛错，不替换已有数据或句柄。

卸载、停用模块不删除分区，不取消已接受修改的提交。未重新申请的历史分区也必须保留，不能因本轮插件集合不同而清理数据。分区删除或更名工具不属于本方案。

## 4. 访问器公共协议

完整类型由 contracts 发布，MemoryManager 实现承诺同一协议；调用方法见使用说明。

| 方法 | 结果及修改语义 |
| --- | --- |
| `query()` | 整个分区的 `DeepReadonly<M>` 引用 |
| `get(key)` / `get(path)` | 路径目标的深只读值；目标或中间层缺失返回 undefined |
| `commit(mutator)` | 同步原地修改，返回回调结果；调用回调前标脏 |
| `commit(key, value)` / `commit(path, value)` | 写入目标，成功返回 void；预检成功后标脏并修改 |
| `remove(key)` / `remove(path)` | 删除存在的目标并标脏，返回 true；目标不存在返回 false 且不标脏 |

不存在“未就绪所以拒绝”的返回值。配置、非法路径和调用阶段错误直接抛错。`commit` 表示接受 heap 修改，不表示持久化完成。

回调无论是否实际修改都标脏；相同值的路径 commit 也标脏。不做深比较、对象代理、自动变更检测或对象树遍历来判断是否发生修改。同一分区同一轮提交前的多次修改合并，只编码一次。

回调必须同步，不得返回 Promise/thenable，不得重入同一分区的修改 API 或宿主生命周期。回调抛错不回滚，已做的修改和脏状态保留，异常交给调用者。回调结果可能是对象引用，不能借此绕过后续 commit 修改数据。

### 4.1 深路径语法与读写边界

顶层键字符串表示一个完整键名，不按点号拆分。深路径采用非空 `readonly (string | number)[]`，允许复用 `as const` 路径。包含点号的房间名、creep 名或其他自定义键按原字符串处理。

- 普通对象用字符串键；数字段只用于数组下标。每一步只访问自有属性，不能沿原型链查找或创建。任何路径段为 `__proto__`、`prototype`、`constructor` 时拒绝。
- 写入要求所有中间容器已经存在。中间层缺失、为 null、基本值或容器类型不匹配时抛错，不自动创建或覆盖。最终对象属性允许新增，但赋值必须符合该属性的完整值类型；动态 Record 的新条目同样要求完整条目值。
- 数组下标必须是非负整数，并且指向已有的自有元素；不自动扩容、制造空洞或创建数组。数组的 length、方法及其他非下标属性不是合法路径。
- `get` 对缺失路径返回 undefined；穿越已存在的基本值或容器类型不匹配属于非法路径并抛错。
- `remove` 支持对象属性；缺失的中间层或目标返回 false。数组元素删除不通过深路径开放，避免隐式移位或空洞；可在回调中显式 splice。
- 空路径不表示整个分区；整体字段组织变化用回调完成，不提供根对象替换方法。

路径写入先完整检查路径、新值及容器条件，再标脏并发布最终修改；同步预检失败不能留下数据修改或脏标记。插入对象若引用目标的祖先必须拒绝：写入保存的是副本，不会真正成环，但这类写入会把整棵祖先子树复制进自身，几乎总是调用错误。路径操作的基本查找成本为 O(路径长度)，新值校验成本另计。

### 4.2 类型推导

顶层重载以 `keyof M` 约束键并关联值类型。路径类型必须支持 readonly 元组、可选属性、动态 Record、数组和元组的元素类型；数组方法名不能进入路径集合。可选/联合类型需分别处理有效对象分支，不能因 undefined 使合法目标值变成 never。

类型检查必须拒绝错误值、错误键、非法数组路径以及对静态必填属性的 remove。动态 Record 项与可选属性可以删除。运行时仍校验输入，类型不能证明反序列化结果、动态键存在性或 JSON 合法性。

可选中间对象或 Record 条目缺失时，调用者须先在其父容器上提交完整对象，或通过同步回调显式初始化完整对象。叶子值类型检查无法构造其他必填字段，运行时也不从 TypeScript 类型推断默认值。例如 `M = { config?: { enabled: boolean; limit: number } }`：`commit('config', { enabled: true })` 必须编译失败；`commit('config', { enabled: true, limit: 10 })` 合法；`commit(['config', 'enabled'] as const, true)` 类型合法，但 config 缺失时运行时抛错且不标脏。Record 新条目按同样规则验收。

深度限制仅约束编译期递归，不隐式限制运行时路径深度。不得通过宽泛的默认重载让普通错误调用绕过类型检查。

顶层键重载与单段路径使用同一套规则，数字索引签名的记录以字符串键访问。路径类型采用“按实参逐段校验”，不枚举业务类型的全部路径：参数写作 `P & NoInfer<ValidPath<M, P>>`，P 只从实参推导，非法路径把参数收窄为 never。编译成本与路径长度线性相关，不随键数量膨胀。递归预算为 8 段（`MaxPathDepth`），超出预算的修改使用 `commit(mutator)`。显式动态入口为 `MemoryAccessor<any>`：放弃编译期路径检查，运行时校验不变。宽 `(string | number)[]` 路径在类型层非法，必须显式断言或改用动态入口。`commit(key, undefined)` 在 strict 类型检查下编译失败，JavaScript 调用方由运行时 JSON 校验拒绝。

### 4.3 JSON 与引用所有权

发布给访问器的分区根必须是普通键值对象，成员为 JSON 值：null、布尔值、有限数字、字符串、数组和普通对象。不接受 undefined、函数、Symbol、BigInt、NaN/Infinity、循环引用、Map/Set、Date、Game 对象、自定义 toJSON 或访问器属性。数组不能有空洞；对象键可包含点号，原型相关保留键不进入受管数据。

初始化、迁移及路径写入的新值在发布前校验；同版本恢复数据在发布访问器前校验。合法工作对象仅经过路径赋值或 remove 修改时，end 直接使用无 replacer 的原生 JSON.stringify 编码，不重复遍历整个分区做 JSON 校验。该优化依赖引用所有权契约：外部别名修改属于协议违规。

每个分区维护 needsFullValidation 标记，初始为 false。在执行 commit(mutator) 回调前同时标脏并将其置为 true；回调空操作、抛错或中断都保留该标记。后续路径写入或 remove 不得清除它。end 只对带此标记的脏分区做完整合法性校验，再用无 replacer 的 JSON.stringify 编码。成功更新该分区候选基线时清除标记；平台接受前的失败不能清除。基线更新中断后的残留脏项即使已清除此标记，其工作对象也已校验且成功提交；之后再次执行回调仍会重新置位。

原型链上的可枚举扩展属性不属于分区数据，校验与 JSON.stringify 一致地忽略，不因其它代码的原型扩展阻断持久化。完整校验负责 JSON.stringify 会静默丢弃、转换或执行的情况，包括 undefined、非有限数字、函数、Symbol 值与 Symbol 键、稀疏数组、自定义 toJSON 和对象上的访问器属性等。数组元素上的访问器、数组的附加字符串属性与对象的不可枚举属性不在检出范围内：它们需要逐元素或逐键额外读取，大型数值数组上约使校验成本增加 10 倍，与降低开销的目标冲突；这些形式属于引用所有权契约下的违规用法，按原生 JSON.stringify 语义写出。收尾不增加独立的环检测遍历；校验器用本次调用局部的已访问对象集合防止无限递归并避免重复遍历共享对象，循环由随后原生 JSON.stringify 抛错，并附所属分区诊断。发布前的新值校验仍须保证路径失败不修改数据，内部循环和指向目标祖先的引用在该预检中拒绝，不另加收尾环检查。

生产构建保留回调分区的完整校验，不能仅在开发构建启用，否则无法保证非法数据不被静默持久化。不扫描 clean 分区；校验辅助集合在调用结束后释放，不跨 tick 保存。

历史记录保留采用 §8 的格式校验规则；只有申请成功后，工作对象才承诺本节的受管数据约束。版本相同时也必须在发布访问器前验证根对象与 JSON 合法性，失败属于分区申请错误，不得退回 initialize。管理器不持有业务 schema，具体必填字段及业务不变量由模块负责校验，不能把通过 JSON 校验等同于证明泛型 M 的运行时结构。

query/get 返回真实对象的类型级只读引用，不默认克隆、冻结或包装 Proxy。路径写入的新值与 initialize/migrate 的返回值一样在校验时复制，调用方保留原对象的所有权；读取返回的引用属于分区，调用方不得通过它修改。commit 回调中直接赋值的对象不复制，由回调负责不让多个分区共享可变子对象。分区内共享子对象可以存在，但不得成环；共享关系不随持久化保留，global reset 后各引用位置解析为互相独立的对象。不同分区的隔离是调用契约，不是针对恶意代码的安全沙箱。

保存的嵌套引用可能因后续字段替换而脱离分区；需要最新值时重新 get/query。直接通过别名修改不会标脏，属于协议违规，不保证持久化。默认不为防止此类违规增加每 tick 扫描成本。

## 5. 持久格式与片段缓存

目标命名空间为 `memoryManager`，schemaVersion 为 2：

```text
主存储根对象
├── 非托管根字段（加载快照）
└── memoryManager
    ├── schemaVersion: 2
    └── partitions[owner][localId]
        ├── dataVersion
        └── payload
```

分区数据版本与 payload 在同一记录中提交。目录容器只负责身份索引，模块业务数据由模块自行定义。所有 JSON 键必须正确转义；不能将 owner/localId 或任意字段名直接插入 JSON 文本。

每个分区持有工作对象、版本、申请配置、稳定访问器，以及一份已提交记录的 JSON 字符串；该字符串按需生成，见下一段。序列化单位是单个 `(owner, localId)` 的完整记录；同一 owner 的不同 localId 也必须独立缓存。

首次加载只解析一次主文本，不重新编码：记录以解析出的 payload 暂存，同版本申请直接把它作为工作对象，不再二次解析；历史记录与非托管根字段在首次拼接整串时才编码为片段，迁移前先编码该记录以固定基线，使 migrate 对输入的修改或抛错不影响已提交内容。旧 leviathan 导入的 payload 在导入时复制，不与保留的根字段共享对象。未申请记录可以暂不创建访问器，其内容始终可用于整串输出。稳态不重复解析主文本；不读取或挂载全局 Memory，不自动探测外部编辑。非托管字段以装载快照保留，其片段不因业务分区 commit 而重新编码。

运行中通过控制台或其他工具修改持久文本不参与 heap 合并，可能被后续写入覆盖；接纳外部编辑需要停止业务写入并重建 global。宿主兼容入口不得引入每 tick 外部根对象扫描，否则无法满足空闲路径的性能约束。

## 6. 标脏与提交

### 6.1 脏集合

成功路径写入、有效 remove 或回调开始时，将所属分区加入去重的待提交集合。同一分区在 end 前的多次修改合并，收尾序列化其最新工作对象。

初始化和成功数据版本迁移同样将分区标脏；命名空间格式升级设置结构变化标记。本 tick 的 end 统一提交这些变化，不另设延迟或强制提交通道。

只维护脏分区集合及结构变化标记。集合为空且无结构变化时，end 直接返回；有变化时遍历脏集合，不为查找修改而扫描全部分区。写入失败保留集合及标记，下一 tick 的 end 按最新工作数据重试。

### 6.2 片段缓存与提交失败处理

分区的已提交片段用于复用 clean 数据和记录最近一次成功提交的基线。工作对象的修改通过脏集合登记；已提交片段只在平台接受完整文本后更新。分区没有独立的延迟快照或提交期限。

收尾步骤：

1. 收集全部脏分区及结构变化。
2. 按 needsFullValidation 标记选择是否完整校验，使用无 replacer 的 JSON.stringify 序列化全部脏分区并建立候选片段；clean 分区继续使用已提交片段。
3. 结合目录与非托管根字段片段拼接完整 JSON，检查主文本容量。
4. 调用平台 writeRaw，一轮 end 最多一次。
5. 平台接受后，先将全部候选片段升级为已提交基线并清除对应 needsFullValidation 标记；整个更新阶段保留脏集合及结构变化标记。
6. 全部基线更新完成后，最后清理脏集合及结构变化标记。提交期间不执行用户回调，不允许重入修改，避免清除尚未编码的新修改。

序列化、拼接、容量检查或平台调用任一步失败，本轮整体提交失败；不推进任何分区的已提交基线，不清脏，保留 heap 修改，下一 tick 重试。本轮候选片段可以丢弃，重试根据最新工作数据重建，避免重复使用失败后已经过时的编码。

### 6.3 无修改的成本承诺

“无 commit 无开销”指稳态持久化工作：

| 条件 | 允许的收尾工作 |
| --- | --- |
| 全部分区 clean，且无结构变化 | O(1) 状态判断；不遍历分区、不解析、不序列化、不拼接、不写平台 |
| 存在脏分区 | 编码全部脏分区；其余对象不遍历，但缓存字符串参与整串拼接 |

初始化、版本迁移、格式升级和历史失败重试属于必须完成的持久化任务，即使本 tick 没有新的 commit。remove 修改了数据也属于显式写入。

拼接和主文本输出与总文本量相关，并非零成本。方案不承诺只写主文本的某个字节区间，也不以 RawMemory.set 的固定 CPU 耗时作为正确性前提。

## 7. 故障、容量与恢复

装载错误和写入错误必须分离。宿主诊断至少包含 `loadError`、`rawWriteError`，诊断只在显式查询时生成快照，记录错误阶段及可定位的 owner/localId；日志按同一原因去重。

- 主文本坏 JSON、未知命名空间版本或无法安全理解的结构：首次 begin 抛错并锁定本 global 的装载故障；禁止写回，也不反复解析同一损坏文本。后续 begin 报告已记录错误。修复持久文本后重建 global。
- 单分区初始化、业务版本迁移或恢复校验失败：申请抛错，不发布访问器；保留历史记录及已提交片段，其他已有效分区不被替换。只缓存管理器判定的确定性失败（缺少 migrate、同版本历史数据不合规）：相同声明再次申请直接重抛，避免每 tick 重复解析与刷日志；修复声明可重新申请，外部数据修复通过 global reset 接纳。用户回调阶段的失败（initialize/migrate 抛错、返回 thenable 或返回值不合规）不缓存，下一次申请重新运行，使违反确定性约束的暂时性失败在条件恢复后可以自愈；插件场景下重试频率由 Framework 熔断限制，recover 后再次重试。
- 写入失败：已有访问器继续读写；保留脏数据，允许模块缩减数据或修正非法值后重试。Framework 不因写入故障自动增加插件失败次数或进入安全模式。

### 7.1 整体提交的故障边界

任一脏分区的非法数据或编码失败都会阻断本轮全部分区的持久化，包括其他模块的关键状态；容量超限同样阻断整串输出。管理器不自动跳过故障分区、不用其旧片段拼出部分成功结果，也不因模块停用而清除该分区的脏状态。这是统一提交协议接受的故障耦合。

诊断须区分分区校验/编码失败、整串容量超限及平台写入失败；分区错误携带 owner/localId，整串错误不能伪造单一故障 owner。调用方可在下一 tick 用有效访问器修正数据或缩减体积后重试。若问题模块已停用，须由仍持有访问器的修复逻辑处理，或修复模块后恢复执行；仅停用插件不能解除持久化阻塞。必要时重建 global 会丢弃所有未持久化 heap 修改，再从有效文本恢复，不是无损修复。自动隔离、分区删除及管理器回滚接口不属于本方案。

### 7.2 宿主与持久性边界

Framework 将 begin 装载异常作为宿主故障处理，执行可行收尾并报告安全模式；setup/钩子内的申请或修改异常进入所属插件错误边界。故障不是等待状态，不返回“下 tick 可能就绪”的句柄。

主文本容量上限采用 2 097 152 个 UTF-16 码元，以 string.length 检查，包括所有命名空间结构和非托管字段。容量超限拒绝整串写入，不覆盖有效文本。实际平台容量及计费行为须由目标环境集成验证，不从本机微基准推断 MMO 性能。

writeRaw 接受调用仅表示本地平台接受，不代表远端数据库确认。CPU 硬终止、宿主未调用 end 或 global reset 都可能丢失未提交 heap 修改。没有跨 tick 回滚或分区间事务承诺。

## 8. 输入格式兼容协议

兼容转换仅发生在首次装载，完成后按 schemaVersion 2 写出。不实现 Segment 回迁。

- schemaVersion 2：验证分区身份、记录版本和容器结构，保留所有分区及非托管字段。记录的 dataVersion 允许非负整数；0 是待业务迁移的历史版本，申请 version 仍必须为正整数。
- schemaVersion 1：以 allocations 的正式归属为准，仅导入 backend 为 raw 的有效 rawPartitions 记录；对应 Raw 记录缺失则报告装载错误，不能当作首次安装。
- backend 为 segment 的身份：忽略目录项及同身份残留 Raw 副本；同名分区申请时执行 initialize。不读取、不激活、不清空页面。首次加载对忽略的 owner/localId 记录一次汇总 warn。
- migration、generationCounter、segmentId、generation 不进入目标格式；不存在正式 Raw 归属的暂存/孤立记录不作为有效分区。有效 Raw payload 和 dataVersion 保留，业务升级另由申请时的 migrate 决定。
- 没有 memoryManager 命名空间时，可导入旧 leviathan.plugins 的对象数据，按 owner/main 建立记录，以 pluginVersions 取版本，缺失版本记 0 并要求业务 migrate；旧 leviathan 根字段原样保留，导入数据不得与它共享可变对象。
- 无法识别的版本或归属结构：保护原文本并报错，不执行猜测性清洗。

历史记录可保留与访问器可发布采用两级校验。装载必须确认记录存在 payload、版本及目录合法，并能无损保留其 JSON 值；历史 payload 允许数组、null 和其他 JSON 基本值，也允许尚不满足受管数据规则的对象。其内容不得被当作目录或沿原型链解释。不能仅因历史根不是普通对象就把整个装载判为失败或当作首次安装。

schemaVersion 1 导入和 schemaVersion 2 重载遵循相同的历史 payload 保留规则。无人申请时，历史片段原义保留并参与整串输出；不要求先运行业务迁移才能完成格式转换。申请版本不同则先把隔离副本以 unknown 交给 migrate，再按 §4.3 校验返回对象；版本相同但不符合受管约束时仅拒绝该分区申请，模块可声明新版本并提供 migrate 修复。迁移失败不改变历史版本、payload 或片段。

缺失版本导入为 dataVersion 0 的记录可以随格式转换写成 schemaVersion 2；即使未申请就发生 global reset，下次仍须成功装载并保留该记录，直到正版本申请显式迁移。不得将 0 在输入时接受、输出后又作为坏格式拒绝。

格式转换本身设置结构变化标记，在本 tick end 强制写出，即使没有业务 commit。首次装载空文本且无人申请时无需为了空命名空间写入。转换写入失败保留原持久文本，reset 后可重复转换。格式转换不承诺被较低 schemaVersion 的程序识别。

## 9. 性能与实现边界

内部职责分为平台适配、格式加载/兼容、分区与访问器、路径校验、片段拼接和提交调度；文件拆分以维护边界决定，不增加同级 Core 隐式依赖。

常驻 heap 包括解析对象、分区索引、访问器、已提交 JSON 片段、脏集合及每分区 needsFullValidation 标记；首次提交前，未申请的历史记录以解析对象形式暂存；提交时还需候选片段和完整输出字符串。缓存以额外 heap 换取避免 clean 对象的重复遍历。整个 global 复用这些容器，reset 重建；每轮候选在成功或失败后释放，不累计历史版本。

深路径的收益是调用便利，不以其作为字段级序列化优化。基准应比较分区数据量、脏比例、分区数和完整主文本大小，观察完整 end 的 CPU、heap/GC 波动及首次装载成本。不得只测单独 stringify 就声称完整提交获得相同比例收益。基准须分别覆盖仅路径写入、仅 remove、回调修改和混合修改；记录输入校验与收尾耗时，不能把提前到写入阶段的校验成本遗漏。回调分区的完整校验可能接近增加一次对象遍历的成本，性能评估须计入，不以带 replacer 的 stringify 作为默认实现。

实施按以下依赖顺序推进：

1. **类型技术验证与协议冻结**：先以 TypeScript 5.9 建立独立类型验证用例，再冻结长期访问器、深路径与宿主错误契约。覆盖字符串键、可选对象、Record、readonly 元组、数组、联合类型、必填属性删除、错误值及错误路径正负例。记录 tsc --noEmit --extendedDiagnostics 的检查时间、实例化数量与内存，并以浅层、递归及大型业务类型验证编译成本；据此确定递归预算及超深动态入口。该步骤以半天至一天为初始时间盒，出现明显编译退化或递归上限时先调整设计并重跑用例，未通过前不进入主体实现，不用宽泛重载绕过负例。
2. **装载和分区缓存**：实现 schemaVersion 2、兼容转换、稳定身份、同步申请、独立片段及 global reset 恢复。
3. **深路径和提交**：实现完整子对象赋值、中间容器存在性检查、路径预检、回调标脏、remove、脏集合、候选片段及成功后清脏。
4. **宿主接入**：Runtime 显式装配；Framework begin/end、装载错误边界及写入诊断；Framework 的 loop 重入锁必须带真实 tick 归属，不得仅靠 running 布尔值与 finally 复位。消费者不依赖等待句柄。
5. **验证和使用文档**：完成下列场景及模块调用说明，记录交付结果。交付使用说明必须明确：单分区非法数据会阻断所有分区写盘及其诊断/修复方式；所有脏分区每 tick end 统一提交，没有管理器节流选项，频繁变化的大数据应按独立修改范围拆分为多个分区，任一分区修改仍编码整个分区且写盘仍输出完整主文本；initialize/migrate 必须使用稳定函数引用，示例将声明提升到模块或稳定实例作用域，覆盖停用再启用和 setup 重试。目标接口未交付前不改写已交付 API 的调用说明，不提供伪装为可运行的新接口示例。

必须验证：

- 多 owner、多 localId、迟到申请、重复声明、卸载重新申请和无消费者历史数据保留。
- 一次 commit 仅编码所属分区，同 tick 多次 commit 合并；同 owner 下另一分区不被重编码。
- clean tick 零对象遍历、零序列化、零拼接、零平台写入；通过脏集合定位修改，不扫描所有分区。
- 所有脏分区在本 tick end 统一提交；初始化或迁移后同 tick 的修改一起提交最新值；写失败后的修改与新增脏分区在下一次 end 合并重试。
- 深路径读取、缺失中间对象拒绝、完整可选对象和 Record 条目赋值、点号键、空路径、危险键、数组边界、基本值冲突、失败无部分写入。
- 缺失 remove 不标脏；回调空操作仍标脏；回调抛错保留部分修改；异步/重入违反契约。
- JSON 非法值、循环/祖先引用、对象别名约定、字段替换后的旧引用与有效片段拼接。
- 装载损坏不覆盖历史数据；分区迁移异常隔离；整串写入失败不推进任何基线；容量超限后缩减并恢复。
- 格式转换可重复，忽略身份的残留副本不复活；整个运行与兼容过程零 Segment API 调用。
- 同 tick 重复 begin/end 不重开阶段；倒退 tick 和同步重入拒绝；遗漏 end 后在新 tick 恢复，清除旧修改锁并保留脏数据。
- 在初始化/迁移发布前、提交编码中、平台接受后及部分基线更新时注入中断，保留 heap 后验证脏集合完整保留并重试；最终清理阶段中断只允许产生冗余提交，global reset 后按平台实际文本恢复。
- 仅路径写入或 remove 的分区收尾不做完整校验；回调、回调抛错及回调后路径写入均需完整校验；写入失败保留校验标记；共享对象校验可终止，循环由 stringify 拒绝，生产构建同样拒绝静默转换类非法值。
- 历史数组、null、基本值和不符合受管约束的对象可以保留、转换格式并再次装载；同版本非法对象只阻断所属分区申请，显式迁移后可发布访问器。
- dataVersion 0 在无人申请时转换为 schemaVersion 2，reset 后可重载，再通过业务迁移升级；迁移失败仍保留原值。
- 一个分区非法时所有分区均不写入；停用问题插件仍保留阻塞及定位诊断；修复后统一提交积累的最新修改。
- 真实引擎跨 tick、global reset、UTF-16 容量、收尾失败和完整提交性能；专门触发 CPU 硬终止并记录目标引擎是否保留 heap，验证 Framework 后续 tick 不被旧 running 状态锁死。模拟保留 heap 的测试不能替代此项环境验证。

代码交付时按 AGENTS.md 依次执行类型检查、测试、无密钥构建和 git diff --check；集成测试覆盖真实引擎恢复。外部上传仅在用户明确要求部署时执行。

待决设计事项仅包括目标环境性能验收阈值：以官方服务器上的完整 end CPU 基准确定，不改变分区序列化粒度或同步可用性契约。编译期递归预算与动态入口已按 §4.2 确定。
