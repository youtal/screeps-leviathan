## 1. 背景与问题

架构 9.2 规定，正常流程创建的 creep 与 spawn 使用统一的签名格式，spawn 的出生用途固定为 `spn`。这一规定对 spawn 有两处不足：

- **首个 spawn 无法带签名。** 只有玩家没有任何对象时才能放置 spawn（F1），每局的第一个 spawn 由玩家在界面中放置并命名。界面默认名为 `Spawn1`（backend 3.3.0 `lib/game/api/game.js` 的 `gen-unique-object-name`），`place-spawn` 原样使用玩家填写的名称，只限制不超过 50 个字符。引擎没有为 spawn 改名的接口（engine 4.3.2 中只有 `PowerCreep.prototype.rename`），这个 spawn 的名称在整局中不变。
- **签名比例的分母因此偏大。** 11.6 的签名比例 σ 同时统计 creep 与 spawn；首个 spawn 与保底 creep 都不带签名，早期殖民地丢失 Memory 时达不到 θ_SELF（[全项目审计](../audit/2026-10-20-project-audit.md) PA-15）。σ 的口径已决定在 M2 实现接手流程时再定。

另一方面，spawn 是玩家在界面上最常看到的名字。用户希望为它留下一个标识性设计：维护一个约 1000 词的词库，本系统创建的 spawn 都从词库中随机抽取名称，不重复使用；开局时也建议玩家从词库中选名放置首个 spawn，但不作强制，也不影响任何判定。

本提案只论证设计，不代表已交付对应代码。

## 2. 设计

### 2.1 词库

- **内容**：约 1000 个词，主题统一。每个词须满足：
  - 不超过 50 个字符，使玩家能在放置首个 spawn 时手工输入（`place-spawn` 的上限），自然也满足创建工地时的 100 个字符上限；
  - 只用 ASCII 字母，避免在日志、控制台与 Memory 键中出现编码问题；
  - 不含 `-`，与 9.2 的 creep 签名格式在语法上互不重叠，`lib.naming` 的解析不会把词库名称误判为签名名称。
- **位置**：作为 lib 中的只读常量（无状态，满足 lib 的边界规则），随构建产物发布。词库变更即改变构建产物，按版本规则递增版本号。
- **存储形式**：一个以空格分隔的字符串，首次需要时再切分为数组并在 heap 中缓存。正常运营中放置 spawn 的频率极低，多数 global 不需要切分。
- **只追加、不改序**：已用记录按词的下标保存（2.3），词库只在末尾追加新词，不删除、不重排，旧记录始终指向同一个词。

### 2.2 抽取

- 由创建 spawn 工地的流程（M2 的 planner 或 build）在调用 `createConstructionSite` 之前抽取名称，取代 9.2 中 spawn 的签名名称与当 tick 序号。
- 从未使用的词中均匀随机抽取，随机源用 `Math.random`；名称不承担身份与唯一性证明，不需要可复现。
- 抽取时排除：已用记录中的词、现存 spawn 与 spawn 工地的名称、本 tick 已预留的名称。引擎在重名时返回 `ERR_INVALID_ARGS`（engine `src/game/rooms.js` 第 1041–1050 行），排除现存名称可避免这类失败。

### 2.3 不重复

- **范围**：同一 shard 的同一局内不重复。一局指从开局（FRESH_START）到下一次重生；FRESH_START 清空 Memory 时已用记录随之清空。
- **记录**：在本系统 Memory 的系统分区中保存已用词的下标位图，1000 个词约需 170 个字符，只在抽取时读写。
- **恢复**：Memory 丢失后，已用记录只能从现存 spawn 与 spawn 工地的名称重建，已被摧毁的 spawn 用过的词无法恢复。这是可接受的退化：名称重复不影响任何功能，引擎只禁止与现存对象重名。
- **耗尽**：每个房间最多 3 个 spawn，词库只在新建或重建 spawn 时消耗，正常运营中一局用不完。耗尽时清空已用记录、只排除现存名称，并记录一条 info 日志。

### 2.4 开局

- README 与运维手册写明：放置首个 spawn 时，建议从词库中选一个词作为名称，并说明词库的位置。
- app.boot 在判为 FRESH_START 时检查首个 spawn 的名称：在词库中则记为已用；不在词库中时记录一条 info 日志提示，不通知、不改变模式判定、不影响后续运营。

### 2.5 与身份判定的关系

- spawn 名称不再承担 9.2 的签名职责，签名格式只用于 creep；`lib.naming` 中 spawn 专用的出生用途 `spn` 随之不再使用。
- 词库公开在代码仓库中，任何人都可以使用这些词，所以"名称在词库中"只能作为 spawn 归属的弱证据。11.6 的 σ 是否、以及如何使用这条证据，在 M2 设计接手流程时与 PA-15 一并决定。

### 2.6 运行成本

- **构建产物**：1000 个词、平均约 7 个字符，加上分隔符约 8 KB，约为当前产物（0.1.12 的 `dist/main.js` 约 18 万个字符）的 4.5%；global reset 时多编译一个字符串字面量。
- **heap**：未切分前是一个字符串；切分后约 1000 个短字符串，只在需要抽取的 global 中出现。
- **CPU**：只在放置 spawn 工地与开局判定时执行，没有逐 tick 成本。
- **Memory**：已用位图约 170 个字符，只在抽取时读写。

## 3. 可选方案与取舍

| 事项 | 方案 | 代价 |
| --- | --- | --- |
| 词库位置 | **lib 常量（建议）** | 占用构建产物，随版本发布 |
| | app.config | 词库不是调参用的配置，放在运营配置中职责不符 |
| | segment | 不占产物，但需要初始化写入，也不随代码版本更新 |
| 不重复范围 | **同一 shard、同一局（建议）** | 跨 shard 可能出现同名，引擎允许 |
| | 全账户、跨 shard | 需要经 InterShardMemory 同步已用记录，依赖 M5 的跨 shard 设施 |
| | 跨局永不重复 | 需要不随 FRESH_START 清空的持久记录（例如 segment），开局判定的清空规则要为它开例外 |
| 首个 spawn | **只提示（建议）** | 不在词库中时只有一条 info 日志 |
| | 不处理 | 失去彩蛋的引导作用 |
| 耗尽 | **清空记录后继续抽取（建议）** | 极端情况下出现跨时段的重名 |
| | 追加数字后缀 | 名称不再全部来自词库 |

## 4. 待确认

1. **词库的语言与主题**。建议用英文单词，主题与项目名 Leviathan 呼应（例如深海、航海与神话），首字母大写，例如 `Abyss`、`Tidewatch`。
2. **不重复的范围**：是否采用"同一 shard、同一局"。
3. **交付时点**：建议本提案确认后更新架构 9.2 与 lib.naming 设计；词库与抽取逻辑随 M2 第一个创建 spawn 的使用方（planner 或 build）一并实现，开局提示随 app.boot 的 FRESH_START 实现（M1 第 6 步）。词库内容可以提前整理。

## 5. 结论

2026-10-21 用户批准，第 4 节三项均按建议采纳：

- 词库使用英文单词，主题与项目名 Leviathan 呼应（深海、航海与神话），首字母大写；
- 不重复的范围为同一 shard、同一局；
- 已更新架构 9.2（spawn 名称改为从词库抽取，签名格式只用于 creep）与 [lib.naming 设计](../design/lib/naming.md)第 4 节。词库与抽取逻辑随 M2 第一个建造 spawn 的使用方实现，开局提示随 app.boot 的 FRESH_START 实现。

11.6 的签名比例 σ 仍按 creep 与 spawn 统计；spawn 不再带签名后，σ 的口径与词库作为弱证据的用法，在 M2 设计接手流程时与审计 PA-15 一并修订。
