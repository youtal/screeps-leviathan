# 基准测试（bench）的形态与设计

| 项目 | 内容 |
| --- | --- |
| 日期 | 2026-10-22 |
| 基线 | `dev`，`ffbd6a9`（0.1.19），加 M2 第 1 步的 lib 实现 |
| 结论 | 已采纳方案 A（2026-10-22） |
| 范围 | 架构 13.1 的 bench；M2 计划中 bench 的交付方式（[M2 计划](./2026-10-22-m2-plan.md)第 9 节） |

## 1. 背景与问题

bench 是 13.1 列出的工程交付物："热路径基准测试"，随 [M2 计划](./2026-10-22-m2-plan.md)第 9 节移入 M2。12.2 要求网格原语单独做基准测试，M2 还有交通结算、成本矩阵与布局规划等热路径。

项目原则规定本地 Node 环境的耗时不能等同于游戏 CPU（第 3 章原则 7），所以 bench 的计量方式要先确定。

## 2. 方案

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| A | 在私服场景镜像中运行，以 `Game.cpu.getUsed()` 计量；输入固定，与保存的基准比较相对变化；同时统计与机器无关的计数 | 每次运行要构建镜像并启动私服，约一分钟 |
| B | 本机 Node 脚本只测相对耗时，用于快速发现回归 | 耗时与游戏 CPU 口径不同，只能作参考 |

私服 driver 以隔离环境的 `isolate.cpuTime` 实现 `Game.cpu.getUsed()`（`@screeps/driver` 的 `lib/runtime/runtime.js`），与官服的计量方式相同；B 的计时包含进程与解释器的其他开销。

## 3. 结论

2026-10-22 采纳方案 A。B 不实施，需要更快的回归检查时再议。

## 4. 设计

### 4.1 组成

| 部分 | 位置 | 职责 |
| --- | --- | --- |
| 计量运行时 | `test/bench/runtime.ts` | 在游戏沙箱内按 tick 预算分批运行用例，记录样本 |
| 用例 | `test/bench/cases/` | 按被测模块分文件，由 `cases/index.ts` 汇总；M2 先有 lib.grid，第 3、5、8 步补充 costMatrix、交通结算与 planner |
| 入口 | `test/bench/main.ts` | bench 专用产物的 `loop`，替代正常的 bot；不读写 Memory、不提交 intent |
| 构建 | `rollup.bench.config.mjs`、`tsconfig.bench.json` | 打包为 `dist/bench/main.js`；`npm run build:bench` |
| 场景 | `test/bench/scenarios/bench.scenario.js` | 在私服世界中运行产物，读取结果，输出单行 `BENCH_RESULT <JSON>` |
| 运行器 | `scripts/bench/cli.ts`、`lib.ts` | 构建镜像、运行场景、汇总、与基准比较、报告；`npm run bench` |
| 基准文件 | `test/bench/baseline.json` | 汇总结果，纳入版本控制 |

bench 不属于 `npm run test:scenarios` 的场景集。镜像与场景测试相同（`test/scenarios/runner`），构建上下文只把场景目录换成 bench 场景，标签为 `leviathan-bench:local`；镜像构建的公共部分在 `scripts/scenarios/image.ts`。容器的隔离参数与场景测试相同：禁网、只读、去掉全部能力、非 root。

### 4.2 计量

- **用例**：`defineCase(name, setup, run)`。`setup` 在计时之外准备固定输入，`run` 为单次迭代并返回工作量计数。同一输入下计数必须每次相同，否则运行时报错。
- **批次**：每个用例先预热，批次内的迭代次数从 1 起倍增，直到一个批次的耗用不少于 1 ms。预热至少 12 个批次，且累计耗用不少于 20 ms。之后按该批次大小采集 30 个样本，每个样本为"批次耗用 ÷ 迭代次数"。
- **tick 预算**：每 tick 已用 CPU 达到 40 后不再开始新批次（私服用户的 CPU 上限为 100）。运行状态保存在 `globalThis` 上，场景逐 tick 以控制台表达式读取，直到完成。
- **堆增量**：取 `Game.cpu.getHeapStatistics()` 中 `used_heap_size` 在批次前后的差值除以迭代次数。它受 GC 影响，只作分配量的近似，不参与判定。
- **工作量计数**：取被测函数的确定性结果，例如距离之和、写入格数。它与机器无关，算法行为改变时随之改变。

### 4.3 判定

| 结论 | 条件 | 是否失败 |
| --- | --- | --- |
| `work-changed` | 工作量计数与基准不同 | 是：算法行为改变，确认后以 `--update` 更新基准 |
| `slower` | 每次迭代 CPU 的 10% 分位数超过基准的 (1 + 容差) 倍，容差默认 0.3 | 是 |
| `faster` | 低于基准的 1 / (1 + 容差) | 否，确认后可更新基准 |
| `ok`、`new`、`missing` | 在容差内；基准中没有；本次没有 | 否 |

判定取 10% 分位数而不取中位数。私服实测中，同一用例的样本会在运行中途整体跳到另一档：`distanceTransform/empty` 的 30 个样本中，前 12 个约 0.0225 ms，其后约 0.044 ms。这是 V8 优化状态的改变，中位数随之波动近一倍；而 10% 分位数在五次运行间的差异在 3% 以内。算法回归会整体抬高样本，同样体现在 10% 分位数上。

基准只在同一台机器上可比，报告同时列出本次与基准的 Node 和引擎版本。

### 4.4 用法

```text
npm run bench                       构建、运行并与 test/bench/baseline.json 比较；工作量改变或回归时退出码为 1
npm run bench -- --update           把本次结果写入基准文件
npm run bench -- --tolerance 0.5    调整回归容差
```

需要 Docker。不读取 `.secret.json`，不访问游戏服务器。

## 5. 验证

- **单元测试**：
  - 计量运行时用假时钟驱动，覆盖批次倍增、预热的两个条件、tick 预算、用例依次完成、计数不一致时报错，并检查用例清单的名称唯一、计数确定（`test/bench/runtime.test.ts`）；
  - 运行器的参数、白名单、结果提取、汇总、判定与报告（`test/scripts/bench.test.ts`）。
- **私服实测**：
  - 连续五次运行，各用例的 10% 分位数差异在 3% 以内，与基准比较全部为 `ok`；
  - 反向验证：把 lib.grid 换回逐方向查表的旧写法后，`bfs` 与 `floodFill` 判为 `slower`（4.6–6.1 倍），退出码为 1，`distanceTransform` 与 `neighbors` 为 `ok`；
  - 同一组数据促成了 lib.grid 的扩展方式调整（[grid 设计](../design/lib/grid.md#4-成本与缓冲区)）：整房 BFS 从约 0.27 ms 降到约 0.06 ms。
