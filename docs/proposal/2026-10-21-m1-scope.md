## 1. 背景与问题

架构 14.3 的 M1 行列出的交付物中，以下几项在 M1 内没有使用方：

| 交付物 | 第一个使用方 | M1 中的现状 |
| --- | --- | --- |
| lib.collections（优先队列、分桶队列、LRU） | M2 的 spawnQueue（按优先级与 deadline 仲裁）、movement（寻路与路径缓存）、world.costMatrix（成本矩阵缓存） | M1 唯一的结果缓存是 errorMapper 的 50 条映射结果，按 `Map` 的插入顺序淘汰已足够 |
| lib.tables（RCL 建筑上限、反应与商品配方） | M2 的固定模板 planner 与 build 使用 RCL 上限；M6 的 labs、factory 使用配方 | 原始数据由游戏全局常量（`CONTROLLER_STRUCTURES`、`REACTIONS`、`COMMODITIES`）提供；tables 的价值在派生查询（例如由产物反查反应物），需要哪些查询取决于使用方 |
| lib.body（身体展开、成本、能力、用途分类） | M2 的 spawnQueue 与接手流程的 adopt 分类器（11.6） | 身体模板在 app.config，两者的接口互相决定 |
| app.config | M2 起的各领域 | [app.config 设计](../design/app/config.md)的成熟度为"定稿 · M2（RCL 1–4）、M3（RCL 5–8）"，与 14.3 把它列入 M1 不一致。M1 没有可放入的内容：Memory 身份是装配常量，使用者开关在 `src/settings.ts` |
| app.profiles（官服与私服的特性开关） | 目前没有 | M1 遇到的官服与私服差异都以运行时特性检测处理：是否提供 `InterShardMemory`（kernel.intershard、身份用的 shard 名）、私服的 `Game.shard` 为主机名（F7）、`Game.powerCreeps` 是否存在（app.boot 的事实读取）。特性检测不依赖人为标注的环境，私服装有插件时同样成立 |
| platformFakes 的 InterShardMemory 与市场部分 | 跨 shard 读写：M5 的 interShard；市场：M6 | M1 已交付 Memory、segment 与 `Game.cpu.halt()` 的严格模拟；kernel.intershard 在 M1 只做特性检测与清空本 shard，现有替身足够 |
| inspector 的迁移工具 | 第一次改变持久结构的发布（13.3 两步迁移） | M1 的 Memory 结构只有 schema 1，没有迁移 |

在没有使用方时先写这些模块，接口只能凭推测确定，与根 AGENTS"不为尚不存在的使用方设计接口"冲突，M2 接入时很可能要返工。这些交付物都不在 M1 的验收标准中，调整不影响验收。

inspector 的查看部分有现成的使用方：线上排障时查看项目标记、单元体积、某个单元的数据，以及备份区与统计页的内容。

## 2. 方案

### 2.1 里程碑安排

| 交付物 | 方案 A（建议） | 方案 B | 方案 C |
| --- | --- | --- | --- |
| lib.collections、lib.body | 移到 M2，与 spawnQueue 同一任务交付 | 留在 M1 | 留在 M1 |
| lib.tables | 移到 M2，只交付 RCL 上限；反应与商品配方随 M6 的 labs、factory 交付 | 留在 M1 | 留在 M1 |
| app.config | 移到 M2（RCL 1–4），与其设计文档一致 | 同 A | 留在 M1 |
| app.profiles | 移出里程碑表，列入 15.2 待补设计："是否需要该模块"在 M2 结束前确定；没有无法以特性检测区分的差异时，从架构中删除 | 同 A | 留在 M1 |
| platformFakes | M1 写明为 Memory 与 segment；InterShardMemory 随 M5、市场随 M6 交付 | 同 A | 留在 M1 |
| inspector | M1 交付只读查看；迁移工具随第一次改变持久结构的发布交付 | 同 A | 同 A |

- **A**：每项随第一个使用方交付，接口由真实需求决定；M1 剩余工作集中在验收标准。代价是 M2 的工作量增加这些模块，但它们在 M2 本来就要被使用，届时设计的接口才是最终接口。
- **B**：只把与设计文档冲突、或可能根本不需要的项移出 M1，lib 三项留在 M1。代价是 lib 三项的接口没有使用方。
- **C**：按 14.3 原样交付。代价同 B，另外 app.config 与其设计文档的成熟度冲突仍需另行处理。

### 2.2 inspector 的形态

| 形态 | 优点 | 代价 |
| --- | --- | --- |
| 本机脚本（建议） | 不依赖 kernel：kernel 因身份或 schema 不符拒绝加载 Memory 时仍能查看；不花游戏 CPU，不增加构建产物；segment 一次请求即得到页内容 | 需要网络访问与账户令牌；每次执行都是对服务器的读取 |
| 游戏内控制台命令 | 不需要本机环境 | kernel 不可用时命令不存在或读不到数据；segment 须先请求激活、下一 tick 才能读取；占用 CPU 与产物体积 |

M1 的运行状态与判定结果已由游戏内的 `ops.status()` 与 `boot.assess()` 提供，inspector 只补足持久数据的查看。

## 3. 建议

采用方案 A，inspector 采用本机脚本。

## 4. inspector 设计（方案 A 采纳后实施）

### 4.1 位置与依赖

- 源码在 `scripts/inspector/`（`cli.ts` 命令行入口，`lib.ts` 纯函数），由 `package.json` 的 `inspect` 脚本调用；与部署工具一样由 Node 的类型剥离直接运行，不进入游戏构建产物。
- 复用部署工具的账户选择与 `.secret.json`（按 `--account` 指定），在 `scripts/deploy/api.ts` 的客户端中增加两个只读请求；segment 的页头解码复用 `src/kernel/segments/page.ts` 的 `decodePage`（该文件没有依赖），与游戏内的编码保持同一份实现。
- 不引入新的依赖：gzip 解压使用 Node 内置的 `zlib`。

### 4.2 平台接口

依据私服后端 `@screeps/backend` 3.3.0 的 `lib/game/api/user.js`（官服实现未开源，以只读请求在官服核实后再声明支持）：

| 接口 | 行为 |
| --- | --- |
| `GET /api/user/memory?path=<点分路径>` | 服务器先对存储的 Memory 文本执行 `JSON.parse`，按路径逐段取值，返回 `{data: 'gz:' + base64(gzip(JSON.stringify(值)))}`；路径不存在时 `data` 为 `undefined`；文本无法解析或中间路径缺失时返回 `{data: 'Incorrect memory path'}` |
| `GET /api/user/memory-segment?segment=<0–99>` | 返回该页的原始文本 `{data}`；从未写过的页为空 |

- 官服多 shard 时请求附带 `shard` 参数；私服后端忽略它。
- **限制**：Memory 文本本身不是合法 JSON 时，服务器不返回原文，inspector 只能报告"无法解析"。这种情况下的原文要从 segment 备份区读取（如果 boot 在清空前完成过备份）。

### 4.3 命令（M1，只读）

| 命令 | 输出 |
| --- | --- |
| `inspect marker` | 项目标记：`sig`、`schema`、`shard`、`epoch`、`lastRun`、`release`、`fp`、`mode`，并按 app.boot 的规则标出 Memory 状态（OURS、OURS_NEWER、FOREIGN 等） |
| `inspect sizes` | Memory 总长度与 2 MB 上限的比例；本项目命名空间中每个单元（系统、分区、实体）的序列化长度，按长度降序；其他根键各自的长度 |
| `inspect get <路径>` | 某个路径下的值，格式化输出；超过长度上限时截断并注明总长度 |
| `inspect segment <页号>` | 页头（owner、epoch、正文长度）与正文；备份区与统计页按各自的格式说明 |

每条命令都必须用 `--account` 指定账户，可选 `--shard`。输出不包含令牌。

### 4.4 验证

- 单元测试：gzip 与 base64 解码、Memory 状态判断、单元体积统计、路径截断、segment 页解码，以构造的接口响应驱动，不访问网络。
- 私服：用场景镜像中的私服后端不能直接验证网页接口（场景框架不启动网页服务），在私服部署演练的环境中执行一次只读查看。
- 官服：在官服非生效分支验证时，经用户同意执行一次 `inspect marker` 与 `inspect segment`，核实接口形状。

### 4.5 迁移工具

随第一次改变持久结构的发布交付：届时按 13.3 的两步迁移设计查看待执行迁移、核对迁移前后的结构与备份。
