## 1. 背景与问题

中央枢纽需要在续命成本、spawn 调度和换代空档之间取舍；世界矩阵需要明确缓存生命周期与成本合成语义；CPU 降级应同时考虑本 tick 预算与执行频率。劳动力、身体模板及孵化优先级随角色发展而变化，不宜反复修订总体架构。

本提案保留本次讨论的论证与决定，不代表已经交付对应运行时代码。

## 3. 成本与平台依据

纯 CARRY、部件数 n 时，每次 renew 增加 `floor(600/n)` tick、耗能 20；长期每 1500 tick 的固定 intent CPU 为 `300/floor(600/n)`，耗能为 `30000/floor(600/n)`。20 CARRY 对应 50 次、10 CPU、1000 能量；这不含调度与补能开销，也不是每个观察窗口都恰好发生 50 次。满负荷交替搬运约 300 固定 intent CPU/1500 tick，因此续命额外约为该搬运成本的 3.3%；闲置时不能沿用此比例。[续命实现](https://github.com/screeps/engine/blob/master/src/processor/intents/spawns/renew-creep.js)、[官方 API](https://docs.screeps.com/api/#StructureSpawn.renewCreep)。

CostMatrix 的非零值替代地形成本；0 才回退到底层地形。原生寻路按访问位置读取，既不预先补齐全房间，也不将地形成本写回矩阵。因此“附加厌恶”必须先与该变体的基础成本合成，不能把附加值直接交给 PathFinder。普通格显式填充能绕过零值分支，但未进行官服性能测量，不能量化收益。[官方矩阵文档](https://docs.screeps.com/api/#PathFinder.CostMatrix)、[原生成本读取](https://github.com/screeps/driver/blob/master/native/src/pf.cc#L98)、[地形位图读取](https://github.com/screeps/driver/blob/master/native/src/pf.h#L198)。

矩阵构建、查询与命名的 CPU 均未实测；本次只确认公开源码行为、公式计算和用户接受的运行取舍。

## 4. 决策边界

- 续命不对普通孵化施加保护性调度；不再采用寿命危险时提升优先级的建议。
- 四种矩阵采用附加成本，障碍优先，道路确定基础成本后再加固定厌恶；不新增 controller 周边厌恶。
- 不引入矩阵性能基准系统、正式物流服务或运行时代码；本次只更新文档。
- 名称唯一性限定为同一世界正常时间线、同一账户及明确的来源 shard；服务器时间回滚与世界重建不被描述为已解决。
- 原工作区的契约开发不纳入本次任务；已讨论的经济层预算规则与预计耗用预检纳入本次架构共识。
