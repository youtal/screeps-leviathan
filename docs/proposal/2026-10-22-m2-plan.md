## 1. 背景与问题

M1 已经发布为 `v0.1.19`，[M1 审查](../audit/2026-10-22-m1-review.md)把若干设计与实现转入 M2。对照架构 14.3 的 M2 交付清单与第 5–11、13 章，发现两处设计缺口：

| 编号 | 缺口 | 依据 |
| --- | --- | --- |
| G1 | 9.6 要求布局计划"编码后存入 segment"，6.8 也把布局计划列为 segment 内容；但 6.8 把读调度与 `SegmentStore` 定在 M5，[segments 设计](../design/kernel/segments.md)写明 `ModuleContext.segments` 在 M5 的读调度上实现。M2 的 planner 写得进 segment，读不回来 | 架构 6.8、9.6；`kernel/segments.md` 第 1 节 |
| G2 | 9.3.5 规定 governor 可调能量的总量由能量回路给出，但 [inventory 设计](../design/colony/inventory.md)的能量设定值表从 RCL4（storage）开始，9.3.4 的现存量也只计 storage、terminal 与 factory。RCL 1–3 的可调预算没有来源 | 架构 9.3.4、9.3.5；`colony/inventory.md` 第 2 节 |

另外，用户决定把原属 M3 的移动、布局能力提前到 M2：movement 的交通冲突结算与 PathFinder 逃离，lib 的 grid 与 layout，world.hub，planner 的道路生长与最小割；planner 不再设固定模板阶段。

## 3. 范围调整

以下交付物从 M3 移到 M2：

| 交付物 | M2 中的使用方 |
| --- | --- |
| lib.grid（距离变换、多源 BFS、洪水填充、邻居迭代） | planner 的核心选址与道路生长、rampart 最小割；defense 的 tower 覆盖 |
| lib.layout（`hubPattern`、核心模板） | planner 设计核心；world.hub 检测枢纽 |
| world.hub | 只报告枢纽事实；中央枢纽 creep 的启用条件需要 link 或 terminal（9.7），仍随 M3 的 logistics 接入 |
| movement 的交通冲突结算（优先级分桶、有界推挤） | 全部移动的 creep；M2 不再需要定义"只有快速路径时如何处理冲突"的过渡规则 |
| movement 的 PathFinder 逃离 | defense 与工作 creep 躲避入侵者 |
| planner 的道路生长与 rampart 最小割 | build 的工地来源；M2 不设固定模板阶段，planner 直接交付最终算法 |

代价：M2 工作量增加，其中 planner 是 M2 中计算量最大的模块，规划须分 tick 执行并依赖 D2 的读调度；收益是 M3 不再替换布局算法，开局建成的基地不会在 M3 迁移到新布局。

仍留在 M3 的有：接手流程的 converge、mineral、logistics 的 link 与中央枢纽、spawnQueue 续命、inventory 的 storage 与 terminal 能量分配与本房矿物、冲刺姿态、app.policy、bench、layoutLab。

## 4. 开发计划

每步是一个从 `dev` 拉出的任务分支，设计文档与代码在同一分支交付；引入跨模块契约的设计文档先经用户确认再写代码。第一个 M2 任务合并进 `dev` 时版本升为 0.2.0。

| 步 | 内容 | 设计文档与契约 | 验证 |
| --- | --- | --- | --- |
| 1 | lib：collections、tables（RCL 建筑上限）、body（展开、成本、孵化时间、能力、用途分类器）、combat（tower 伤害、治疗与伤害估算）、grid、layout；app.config 的 RCL 1–4 表与加载校验 | `lib/*.md`；纯函数，没有跨模块契约 | 单元测试 |
| 2 | **契约先确认**：`ServiceResolver` 及 world、services 的注入方式；creep 与 room 的 core 切片类型、`core(key)` 只读视图与写入接口；sense 阶段的 creep 分组与遗留池；`admit`；`ModuleContext.stats`；`ModuleContext.segments`（`SegmentStore`、`PENDING`）。kernel：实例准入过滤、殖民地份额、AMBIGUOUS 排除非生存层（[boot](../design/app/boot.md) Q2）、实体切片索引（S-25）、硬终止归因（S-06，届时决定）；segments 的读调度（优先级与等待时长、最多 10 页、预热顺序、读后退出激活集）及 epoch 起点问题（[bootPort](../design/kernel/bootPort.md)）。确认新增分区是否改变 schema 版本，改变时按 13.3 两步迁移并交付迁移工具 | contracts README、`kernel/{cpu,memory,segments}.md` | 单元、严格平台模拟、边界、混沌 |
| 3 | world：roomCache；costMatrix（A、B 两层，四种变体，两级失效，`invalidate`）；threat（本房识别）；hub | `world/*.md` | 单元；costMatrix 合成结果与原生寻路语义对照 |

| 7 | domains：bootstrap（生存层）、mining、upgrade、logistics（房内自行调度） | `domains/economy/*.md` | 私服：开局到 RCL2 |

## 5. 上线与验收

按 14.1 的"私服回归 → 默认暂停上线 → 逐项启用 → 观察 → 默认启用"发布；每次上线前运行 13.2 的全部检查，包括"上一版本 → 新版本 → 回滚"的场景。

| 阶段 | 时机 | 内容 |
| --- | --- | --- |
| R0 | 首次官服发布前 | 清理官服上的演练与测试分支（PA-13）；按 D1 确认重生与放置 spawn 的时机；以 `boot.dryRun` 观察判定结果 |
| R1 | 第 7–10 步完成后 | 首个 M2 官服版本（`master` 标签）；新领域默认暂停，按生存、经济、维护的顺序以 `ops.resume` 逐个启用 |
| R2 | 第 11–12 步完成后 | 增量上线接手流程与可观测性；开始计 `T_BASELINE` |
| 验收 | R2 之后 | 14.2 闭环运行基线 6 条；RCL1→4 无人工干预；击退 NPC 入侵（开局本房阈值为 1000000，F2）；接手时 stabilize 无资产损失（私服）；10.8 指标达标或建立基准；人为触发一次告警，验证告警链路 |
| 校准 | 观察期内 | 以实测值校准 5.3 的目标值与 cpu 设计的 `MAINTENANCE_PERIOD`、`CPU_EMA_ALPHA`；在官服确认 15.1 中 segment 写入是否要求页处于激活状态、首个 spawn 是否自动开启 safe mode |
| 收尾 | M2 结束前 | 决定 app.profiles 的去留（15.2）；M2 里程碑审查与成熟度更新；`dev` 合并到 `master` 并打标签 |

## 6. 风险

- planner 的道路生长与最小割是 M2 中最重的计算，规划层受 bucket 门槛约束（5.2），开局时规划须在 bucket 允许的范围内分 tick 完成，规划完成前 build 没有工地来源，bootstrap 只能采集、补能与升级。
- 私服刷出 NPC 入侵者需要同扇区有入侵者据点；场景注入做不到时，官服是入侵防御的唯一真实证据，验收进度随官服时间推进。
- M2 第一次加入业务分区与切片；若改变 schema 版本，须两步发布。
- 6.8 中情报（7.2，M4）放在按 hash 分片的 10–29 页，而分片 store 在 M5；该问题不在本次范围内，在 M4 设计 intel 时处理。
