## 问题

### DV-01 · P2 · 人工指定开局绕过 autoClear 与 OURS_NEWER 的保护

**类别：范围内修正，其中 autoClear 部分需要你在设计上取舍。证据：源码确认、平台替身复现。**

- **来源**：
  - [assess.ts](../../src/app/boot/assess.ts#L103) 第 103–107 行：`assess()` 在检查 OURS_NEWER（第 108 行）之前处理 `force`，`FRESH_START` 且 Memory 不是 EMPTY 时一律给出 `clear`；
  - [index.ts](../../src/app/boot/index.ts#L264) 第 264 行：`!options.settings.autoClear && v.case !== 'force'`，人工指定不受 `autoClear` 约束。
- **设计依据**：
  - 架构 11.4 情形 e（第 1288 行）：OURS_NEWER "禁止清空"；
  - 架构 11.8（第 1396 行）：清空须"配置允许（`boot.autoClear`）"；
  - [boot 设计](../design/app/boot.md) 第 172 行：`boot.force` "发布该模式并按第 6 节执行"，第 6.1 节的前置条件 3 是 `autoClear`。
- **复现**：Memory 的 schema 为 2、代码为 1，`autoClear` 关闭，调用 `boot.force('FRESH_START')`。之后经软重置、备份，Memory 被清空并重建为 schema 1、epoch 1。
- **影响**：回滚到旧版本后误用该命令，会清掉新版本的数据。清空前已备份，数据可从备份区取回，但违背了 11.4 e 的保护。`autoClear` 关闭时人工指定仍能清空，与 11.8 的文字不符。
- **级别说明**：Codex 定为 P1。需要人工显式调用，并且先经过备份，所以调为 P2。

**选项：**

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| A（建议） | OURS_NEWER 时人工指定也不清空，改判 AMBIGUOUS 并说明原因。`autoClear` 的约束改为在设计中写明："`autoClear` 只约束自动清空，`boot.force('FRESH_START')` 是人工确认，不受它约束" | 需要你授权修订架构 11.8 的文字。`BootSettings` 注释本来写的就是"是否允许自动清空"，与现行代码一致 |
| B | 严格按现行设计：人工指定同样受 `autoClear` 与 OURS_NEWER 约束 | 不改章程。代价是 `autoClear` 关闭时，b′ 的"经 `boot.force` 确认后再清空"无法完成：`autoClear` 是构建期设置，只能改设置后重新部署 |

### DV-02 · P2 · 关闭 dryRun 后不重新判定

**类别：范围内修正。证据：源码确认、平台替身复现；"随后判为 NORMAL"为推断。**

- **来源**：[index.ts](../../src/app/boot/index.ts#L363) 第 363–366 行，`boot.dryRun` 的设置函数只给 `dryRunOverride` 赋值，没有设置 `rejudge`。第 385 行在下一 tick 照常调用 `maintain()`。
- **传播**：dryRun 期间判定的动作没有执行。关闭后，如果廉价不变量没有突变，就不会再完整判定，动作继续被漏掉；`maintain()` 却恢复写入 `lastRun`。
- **复现**：Memory 属于本系统、世界为重生（11.4 c）、设置为 dryRun。首个 tick 判定后在控制台关闭 dryRun，再运行 2 个 tick：`lastRun` 从 1 变为 1003，epoch 仍为 0，没有备份与清空。
- **影响**：重生证据"`lastRun` 早于放置"被覆盖。之后本实例内出现完整判定时，判定会落入 11.4 d（推断，复现宿主在重建时会回到设置中的 dryRun，未走到这一步）。按设计，dryRun 正是部署到新环境时先观察、再关闭的开关，这条路径会在首次部署时出现。
- **建议**：dryRun 的值变化时登记完整判定（`rejudge = true`）；补充"关闭 dryRun 后下一 tick 执行判定的动作"与"关闭后不覆盖重生证据"的测试。

### DV-03 · P2 · AMBIGUOUS 期间离开开局世界后指纹解冻

**类别：范围内修正。证据：源码确认、平台替身复现。**

- **来源**：[index.ts](../../src/app/boot/index.ts#L326) 第 326 行，`fpFrozen` 只在本次情形以 `11.4` 开头时成立；第 347–349 行的 `maintain()` 随之写入指纹。
- **传播**：11.4 c′ 判为 AMBIGUOUS（房间在指纹中）。之后 creep 数从 0 变为 1，W 不再成立，判定落入 `11.7 OURS 保持 AMBIGUOUS`，`fpFrozen` 为 false，指纹写入当前 spawn。creep 死亡，W 再次成立，`known` 为真，判为 11.4 d NORMAL。
- **复现**：指纹中为 `old`、当前 spawn 为 `new`、时钟不可用。creep 数按 0 → 1 → 0 变化，模式依次为 AMBIGUOUS → AMBIGUOUS（指纹被写为 `new`）→ NORMAL，epoch 不变，没有人工确认。
- **影响**：ultrareview 第 2 项的修复不完整。M2 起生存层会孵化 creep，creep 在控制器升级前死亡就能形成这一路径。
- **建议**：项目标记的模式为 AMBIGUOUS 时，到人工确认之前一律不写指纹，不再以本次情形是否属于 11.4 为条件。补充"W 往返"与"其间 global reset"的测试。

### DV-12 · P2 · API 客户端缺少 X-Username，私服上无法认证

**类别：范围内修正。证据：源码确认、私服实测。**

- **平台事实**：私服后端 `@screeps/backend` 3.3.0 用 `passport-token` 0.2.0 认证（`lib/game/api/auth.js` 第 10、80 行）。该策略从 `x-username` 与 `x-token` 两个请求头取凭据，缺任何一个都直接判为"缺少凭据"（`passport-token/lib/strategy.js` 第 84–88 行）。后端的校验回调不检查用户名的值。官服只需要 `X-Token`（部署工具此前在官服上传成功）。
- **来源**：[api.ts](../../scripts/deploy/api.ts#L127) 第 127 行，请求头只有 `Content-Type` 与 `X-Token`。
- **实测**：本机私服上，同一个有效令牌只带 `X-Token` 时 `GET /api/auth/me` 返回 401；加上 `X-Username` 后返回用户，分支列表与 Memory 读取都成功。
- **影响**：部署工具与 inspector 在私服上的所有请求都失败，阻断 M1 验收标准"部署、分支切换与回滚在私服完成演练"。
- **建议**：每个请求附带 `X-Username`，取值为账户名（`.secret.json` 的键名），并在 API 客户端注释中写明这一平台差异；补充请求头的测试。

### DV-04 · P3 · 连续被刹车时连续落选次数恒为 1

**类别：范围内修正。证据：源码确认、单元复现。**

- **来源**：[cpu/index.ts](../../src/kernel/cpu/index.ts#L253) 第 253 行，`judge()` 准入时把 `starve` 清零；第 307–311 行的 `brake()` 只加 1。
- **复现**：同一进程连续 4 个 tick 执行"准入 → 刹车 → 结算"，连续落选次数依次为 1、1、1、1。
- **依据与影响**：[cpu 设计](../design/kernel/cpu.md) 第 87 行要求刹车后"连续落选次数加 1"。现在等待时间被低报，连续被刹车的进程在下一 tick 的优先顺序中排在实际等待更久的进程之后。不会导致停摆（每 tick 仍按落选者优先判定），所以定为 P3。
- **建议**：准入时不清零，改在 `settle()` 确认结果仍为准入时清零；补充连续刹车、预算落选后又被刹车的测试。

### DV-05 · P3 · 覆盖生效分支时历史校验晚于上传

**类别：范围内修正。证据：源码确认，未执行部署。**

- **来源**：[cli.ts](../../scripts/deploy/cli.ts#L139) 第 139 行在 `upload()` 中先调用 `api.uploadCode()`，第 148 行才进入 `activateAndConfirm()`，历史文件在后者中读取与校验（第 81 行起）。
- **影响**：覆盖当前生效分支（必须带 `--activate`）且历史文件损坏时，线上代码已被覆盖，命令随后报错退出，回滚也被损坏的历史阻断。ultrareview 第 4 项的修复只覆盖了单独的 `activate`。
- **建议**：`upload --activate` 在第一次写服务器之前读取并校验历史，把结果传给激活步骤。

### DV-08 · P3 · 混沌测试的扰动统计不能证明扰动生效

**类别：范围内修正（测试）。证据：源码确认、变异验证。**

- **来源**：[chaos.test.ts](../../test/chaos/chaos.test.ts#L264) 第 264 行，`starved` 只要求"CPU 被压低、worker 未运行、当前没有注入故障"，没有排除 worker 已经熔断；第 299 行恢复阶段无条件调用 `reset()`，与随机 reset 共用同一个计数，第 322 行的 `resets > 0` 因此恒真。
- **变异验证**：临时禁用 kernel 的预算落选与紧急刹车后，6 项混沌测试仍全部通过。
- **影响**：CPU 保护失效时，测试仍声称覆盖了"经济层因 CPU 不足未运行"。
- **建议**：只统计未熔断、因预算落选的 worker；随机 reset、halt 后重建与恢复阶段的 reset 分开计数；以上述变异作为反向验证。

### DV-06 · P4 · 同分支激活挤满历史窗口

**类别：范围内修正。证据：源码确认。**

- **来源**：[lib.ts](../../scripts/deploy/lib.ts#L380) 第 380–381 行，`appendActivation()` 无条件追加并只保留最近 100 条；第 398 行回放时跳过 `from === to` 的记录。
- **影响**：一次真实切换之后，再有 100 次同分支激活（覆盖生效分支时每次都会产生一条），真实切换记录就被挤出，生效栈为空：不能一步回滚，上一个生效分支也失去删除保护。需要的操作次数较多，定为 P4。
- **建议**：`from === to` 的记录不写入历史（已有的仍在回放时跳过）。

### DV-07 · P4 · sizes 的总长度不是原文长度

**类别：范围内修正（文案）。证据：源码确认。**

- **来源**：[inspector/lib.ts](../../scripts/inspector/lib.ts#L237) 第 237 行以 `JSON.stringify(read.value).length` 作为"Memory 总长度"。服务器先解析原文再重新序列化，原文中的空白与转义写法不保留。
- **影响**：本项目 kernel 写入的是紧凑的 `JSON.stringify` 结果，两者相同；外来或手工编辑过的 Memory 会被低估。Codex 定为 P3，因只影响非本项目写入的 Memory，调为 P4。
- **建议**：输出与 README 写明"重新序列化后的长度"，并说明外来 Memory 的原文可能更长。

### DV-09 · P4 · chaos 场景的"每 tick 提交"断言过宽

**类别：范围内修正（测试）。证据：源码确认，未运行私服。**

- **来源**：[chaos.scenario.js](../../test/scenarios/scenarios/chaos.scenario.js#L114) 第 114 行，推进 20 tick 后只断言 `lastRun >= squeezedFrom + 20`。只要最后一次提交发生，中间的提交全部跳过也能通过。
- **建议**：逐 tick 读取 `lastRun` 并断言每次都前进；或者把断言说明收窄为"压低 CPU 期间正常循环仍在推进"。

### DV-10 · P4 · 冻结证据时 release 不更新

**类别：范围内修正。证据：源码确认、平台替身复现。**

- **来源**：[index.ts](../../src/app/boot/index.ts#L385) 第 385 行，`frozen` 时整个 `maintain()` 被跳过，包括第 346 行每个实例首次写入的 `release`。
- **依据**：[boot 设计](../design/app/boot.md)第 6.1 节只要求冻结 `lastRun` 与 `fp`，第 7 节要求每个实例首次就绪时写入 `release`。
- **复现**：旧标记的 `release` 为 `test`、当前为 `newRelease`，重生清空被 `autoClear` 拦下后，标记中仍为 `test`。
- **建议**：`release` 的写入与证据维护分开。

### DV-11 · P4 · 注释规则的执行口径与既有缺口

**类别：范围外，只报告。证据：源码确认。**

- **对象参数的 JSDoc**：README 要求"对象参数用 `@param opts.字段` 逐项说明"。`createBoot`（[index.ts](../../src/app/boot/index.ts#L125) 第 125 行）只写了 `@param options` 的总述，字段说明在 `BootOptions` 接口上。同样的写法在 `src/` 的 10 个文件中都有，上次全项目审计也未列为问题。只修改本轮新增的一处会与其余代码不一致。
- **平台替身的既有缺口**：[memory.ts](../../test/platform/memory.ts#L203) 第 203 行的 `saved` Map 缺少 key/value 含义注释，第 230、233 行的 getter 缺少 JSDoc。这些自 M1 第 1 步就存在，本轮只增加了 halt 选项。
- **建议**：由你决定口径：参数类型是带字段注释的接口时，是否视为已逐项说明。如果不视为已说明，就批量补齐 10 个文件；如果视为已说明，就在 README 中写明（README 属于章程，须你的指令）。平台替身的缺口可以随下一次修改该文件时补齐。
