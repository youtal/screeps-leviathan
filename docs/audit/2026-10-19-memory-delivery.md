## 问题

### MA-01 · P2 · 同一 tick 新建的 creep/flag 记录被维护扫描删除

**类别：范围内修正。证据：源码确认、测试复现。**

- **来源**：[entities.ts](../../src/kernel/memory/entities.ts#L134) 第 134–138 行的回收条件只依据 tick 开头采集的事实：
  - creep 在"上一 tick 名称集合"和"本 tick 名称集合"中都不存在即回收；
  - flag 在本 tick 名称集合中不存在即回收。

  `of()` 新建记录时把它加入 `state.records`（第 85 行），而维护游标是这张 Map 的活动迭代器（第 30 行、第 125–126 行）。按 Map 迭代语义，游标尚未经过的位置追加的条目，在同一轮扫描里会被访问。
- **传播**：
  - 架构 6.5 规定 creep 记录在 `spawnCreep` 返回 `OK` 的当 tick 写入，flag 记录在模块首次写入时创建；
  - 而新 creep、新 flag 要到下一 tick 才出现在 `Game.creeps`/`Game.flags` 中，当 tick 的事实里必然没有它们；
  - 宿主如果在实体写入之后运行 `maintain`（维护层位于各领域的 plan、act 之后），新记录在当 tick 就满足回收条件。
- **影响**：新 creep 的归属与任务记录被静默删除。下一 tick 它出现在 `Game.creeps` 中却没有记录，按 9.1 进入遗留池；flag 的同类数据直接丢失。记录总数少于维护上限时，每次都会触发；记录较多时，取决于游标位置。
- **复现**：在临时副本中新增测试，保留原实现：

  | 场景 | 结果 |
  | --- | --- |
  | tick 2 写入 `creeps.of('newborn')` 后调用 `maintain`；tick 3 事实中出现 `newborn` | tick 3 时 `has('newborn')` 为 false，持久文本中 creeps 为空 |
  | 同一序列，改为先 `maintain` 后写入 | 记录保留，说明结果取决于宿主的调用顺序 |
  | tick 1 写入 `flags.of('Flag1')` 后同 tick `maintain` | 持久文本中 flags 为空 |
  | 已有 60 条记录、上限 40：新记录追加后的那一轮扫描 | 新记录被访问并删除 |

**选项：**

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| A（建议） | heap 中为每条实体记录保存创建 tick；creep 只回收创建至少 2 tick 的记录，flag 只回收创建至少 1 tick 的记录 | 每条记录多一个数字字段，不进入持久文本；global reset 后已有记录按加载 tick 计，最多推迟 2 tick 回收 |
| B | 在宿主契约中规定 `maintain` 必须早于本 tick 的任何实体写入 | 无运行成本，但正确性依赖调用顺序，容易在装配变化时失效，且无法由 Memory 自身检查 |

修复后应补充以上四种场景的回归测试，并做反向验证。

### MA-02 · P2 · 单个单元的非法值阻塞全部模块的持久化

**类别：范围内修正（需取舍）。证据：源码确认、测试复现。**

- **来源**：
  - [accessor.ts](../../src/kernel/memory/accessor.ts#L83) 第 83–92 行，`update` 标脏后把原引用交给回调，按 6.3 不回滚；
  - [commit.ts](../../src/kernel/memory/commit.ts#L58) 第 58–63 行，对所有脏单元逐个执行 `validateJson`，任一单元抛错，整次提交就中止，脏集合保留。
- **传播**：某个模块的 `update` 留下非法值（例如显式 `undefined`）后，该单元每 tick 都在脏集合中，每次 `commit` 都在校验它时抛错。其他模块的合法修改即使已写入 heap，也随之无法持久化。直到问题数据被修正或发生 global reset 为止，而 reset 后会丢失这期间全部模块的修改。
- **违反的依据**：架构 5.1 的故障隔离与熔断以进程为单位；模块设计"保留上一版持久文本"的原意是保护出错的单元。当前实现把一个模块的数据错误放大成全体持久化停止，进程熔断也无法使其恢复，因为非法数据仍留在 heap 中。
- **复现**：模块 A 的 `update` 把字段设为 `undefined`，模块 B 同时 `set` 合法值。tick 2–5 的每次 `commit` 都抛 `TypeError`，持久文本中 B 的值始终为初始值 0，写入口只在初始化时调用过 1 次。

**选项：**

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| A | 维持现状：任一非法单元阻止整次写回 | 实现最简单；故障影响全体，且没有自动恢复路径 |
| B（建议） | 单元级隔离：校验失败的单元沿用上一次成功的编码（新建单元则暂不写入），保持脏状态，通过告警端口报告单元身份；其余单元照常提交 | 每个脏单元一次 try/catch，没有额外遍历；需要明确"该单元持久文本停留在上一版"的语义，并在设计文档中更新 |
| C | 在 B 的基础上，由 `update` 在回调返回后立即校验目标子树，把错误抛给出错的模块 | 每次 `update` 多一次子树遍历；能更早定位责任模块，但仍需要 B 来保证其他模块不受影响 |

### MA-03 · P2 · 空存储与外来根键的处理和架构 11.3/11.4 冲突

**类别：范围内修正（模块设计须服从架构）。证据：源码确认、测试复现。**

- **来源**：
  - [runtime.ts](../../src/kernel/memory/runtime.ts#L162) 第 162–167 行：只有完全没有根键时才视为空存储，存在任何其他根键而缺少本系统命名空间就抛出"外来 Memory"，并由 `beginTick` 锁存为实例失败（第 269–273 行）；
  - `initialize` 只允许空根（第 290–297 行）；
  - [模块设计](../design/kernel/memory.md)写明"初始化只接受空文本或空根对象"。
- **与章程冲突**：
  - 11.3 把"根键只有 `creeps/spawns/rooms/flags/powerCreeps` 且值都是空对象"定义为 `EMPTY`，11.4 情形 a 要求直接初始化；
  - 11.4 情形 b′（FRESH_START 中证据，属于 M1）要求"不清空：外来键只读保留，本系统照常初始化并运营"；
  - 11.5 情形 b 与 11.6 的 stabilize（M2）也要求外来数据只读保留。

  这些路径在当前实现下都走不通：实例在加载阶段即锁死，同一 global 内无法再初始化。
- **复现**：

  | 初始文本 | 结果 |
  | --- | --- |
  | `{"creeps":{},"spawns":{},"rooms":{},"flags":{},"powerCreeps":{}}` | 连续两个 tick 的 `beginTick` 都抛"外来 Memory"，`initialize` 报"Memory 不可初始化" |
  | `{"foreignBot":{"x":1}}` | `beginTick` 抛"外来 Memory" |

**选项：**

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| A（建议） | 加载结果增加 `foreign` 状态，不作为锁存失败；`initialize` 在宿主授权后接受非空根，本系统命名空间与其余根键并存，其余根键按现有 peers 缓存只读保留。是否把 11.3 的空对象形状视为 `EMPTY` 由 boot 判定，Memory 只执行"保留或丢弃这些根键"的显式指令 | 需要改宿主接口（`beginTick` 返回值、`initialize` 参数）和模块设计；业务契约不变 |
| B | 维持 Memory 严格，要求 boot 在初始化前先备份并清空 | 与 11.4 b′"不清空"直接矛盾，须修订章程，不建议 |

### MA-04 · P3 · 低于代码支持版本的根 schema 无法加载

**类别：范围内修正（可延后）。证据：源码确认、测试复现。**

- **来源**：[runtime.ts](../../src/kernel/memory/runtime.ts#L139) 第 139–141 行的 `checkMarker` 要求 `schema` 与配置严格相等，加载第 170–171 行因此拒绝较旧的 schema。
- **依据**：11.3 把 `schema` 不高于代码支持版本的项目标记归为 `OURS`；6.7 规定 `schema` 在迁移时更新。按此，旧 schema 应能加载并迁移；只有较新的 schema 才应进入 `OURS_NEWER`。
- **影响**：当前只有 schema 1，没有现时影响。第一次提升根 schema 时，线上 Memory 会在加载阶段锁死，boot 无法区分"旧版本待迁移"与"外来数据"。
- **复现**：持久文本 schema 为 1、代码配置 schema 为 2 时，`beginTick` 报"schema 不匹配"。

**选项**：A（建议）把限制写入模块设计的"已知限制"，在第一次提升根 schema 的任务中实现根级迁移（届时才有使用方，按"不为尚不存在的使用方设计接口"）；B 现在就增加根级迁移接口。两者都需要同时说明 `OURS_NEWER` 下 Memory 的行为：建议只读加载、拒绝写入，供 AMBIGUOUS 的生存层读取。

### MA-05 · P3 · 只经 `set`/`replace` 写入的单元在提交时被再次完整校验

**类别：简化。证据：源码确认、调用计数复现。**

- **来源**：
  - `set`/`replace` 写入前已用 `copyJson` 完整校验并复制（[accessor.ts](../../src/kernel/memory/accessor.ts#L68) 第 68–74 行、第 118–123 行）；
  - 但 [commit.ts](../../src/kernel/memory/commit.ts#L58) 第 58–63 行对所有脏单元再次执行 `validateJson`。

  校验遍历时，每个属性都要分配一个属性描述符对象（[json.ts](../../src/kernel/memory/json.ts#L64) 第 64 行），数组的每个下标还要执行一次正则（第 60 行）。
- **复现**：对 1000 个元素的数组执行一次 `set`，写入阶段读取属性描述符 1000 次；同一 tick 的 `commit` 又读取 1004 次。
- **运行依据**：只有经 `update` 原地修改的单元才可能在写入后变成非法数据。按"是否经 `update` 修改"标记单元，提交时只校验带标记的单元。这样对只经 `set`/`replace` 写入的脏单元，每 tick 可省去一次完整遍历及其描述符分配，GC 压力随之下降；收益规模以计数确认，Screeps CPU 收益未测量。
- **代价与边界**：每个单元增加一个 heap 布尔值。有一处行为差异：模块如果违反只读约定、直接修改了 `get` 返回的引用，现在这类非法值会在提交时被拦下，改动后会按 `JSON.stringify` 的规则被静默省略。建议同时说明开发期抽查覆盖这种违规的范围；如果不接受这一差异，可以维持现状。

## 范围外问题

- **CORRUPT 情形的章程表述**（architecture 11.4 b′）：对 `CORRUPT` 要求"外来键只读保留"，但无法解析的文本没有可以保留的键；本系统一旦写入主 Memory，原文本就被覆盖。建议明确为"先备份到 segment 备份区，再初始化"，或者在时钟不可用时禁止写入。这需要修订最高章程，只报告，不处理。

### MA-01：保留 P2，修正根因说明

**类别：范围内修正。** 原报告“新 creep、新 flag 要到下一 tick 才出现在 Game”不准确。公开引擎源码中，spawnCreep 成功路径直接赋值 `globals.Game.creeps[name]`，createFlag 成功路径直接赋值 `globals.Game.flags[name]`，均在当前调用内完成：见 [structures.js 的 spawnCreep](https://github.com/screeps/engine/blob/master/src/game/structures.js#L1047) 与 [rooms.js 的 createFlag](https://github.com/screeps/engine/blob/master/src/game/rooms.js#L952)（本轮公开源码核实，非私服运行）。

真正的传播链是 [runtime.ts 的 beginTick](../../src/kernel/memory/runtime.ts) 第 264–265 行复制了名称 Set，后续创建不会进入该快照；[entities.ts 的 maintain](../../src/kernel/memory/entities.ts) 第 134–138 行仍用旧快照回收。即使宿主把原始 Set 更新成当前 Game 名称，副本仍不会变化。因此缺陷结论保留，不能据错误的平台前提否定或修复它。

建议采纳 A 的新记录保护思路。创建 tick 必须属于整条实体记录；增加其他 owner 切片不能刷新既有记录的创建时间，否则会反复延长回收。既有记录加载时如何计龄、跳 tick、同名重建均应明确并覆盖测试。B 的调用顺序约束虽然能规避特定场景，但把正确性留给装配，不建议。原报告“维护层位于 act 后”也不应作为已固定契约：4.4 固定了流水线，当前模块只规定维护准入与宿主调用，尚无 main 装配。

### MA-02：保留风险，撤回“违反模块设计原意”的断言

**类别：设计取舍；若新增单元隔离降级，则属于新增功能，须用户确认。** [模块设计](../design/kernel/memory.md) 第 52 行明确要求非法值阻止本次写回、保留上一版持久文本；第 62 行要求完整候选文本准备后才写入。现有行为遵守该契约。架构 5.1 的进程级故障隔离不能直接推出单元级部分提交，也不能把“上一版持久文本”自行解释成“出错单元的上一版文本”。

选项 A 是保持已批准的整次拒绝语义；B 是新增降级语义，故障持续时健康单元可推进，但会形成不同版本单元的混合快照。若选择 B，应先补设计决策：首次 global reset 提交时没有 encoded 基线如何处理；新单元不落盘如何处理索引/空实体；失败单元如何继续标脏及重试；尺寸统计、待确认文本及 commit 返回值如何反映部分成功；重复错误如何避免每 tick 日志刷屏。不能把成本仅概括为“一次 try/catch、无额外遍历”。C 仍不替代提交隔离，且增加 update 路径扫描。

本轮建议维持 A，不把 MA-02 当作违反当前契约的 P2 合并阻断；保留其跨模块故障影响说明。如果目标改为健康单元必须独立推进，再单独批准 B 的完整设计与实施。

### MA-03：保留 P2，接受方向但约束授权边界

**类别：范围内修正，涉及宿主接口调整需用户确认。** 架构 11.3 的 EMPTY 形状、11.4 a 及 b′ 确实无法由当前严格初始化入口实现。当前 main 未接入并不能消除此集成缺口。

建议采用 A：Memory 能加载并保留合法对象根，识别“本项目命名空间缺失”，由 boot 决定初始化资格；初始化操作只能在宿主明确授权后添加项目命名空间。不能将“允许与外来根键共存”扩大为覆盖已占用的同名命名空间、绕过较新 schema 或自动清空。状态是否叫 foreign、是否需要增加 initialize 参数，应按最小宿主接口确定，不能同时把 boot 世界判定搬进 Memory。B 与“不清空”场景冲突，不采纳。

### MA-04：保留 P3，延后迁移实现，修正建议落点

**类别：范围外问题（未来根 schema 升级），本次仅记录限制。** 旧 schema 的识别与旧结构迁移是两件事；不应为了让分类符合 OURS，直接把未知结构当作当前 Namespace 加载。首次根 schema 升级时应明确支持哪些旧版及迁移规则，再实施使用方需要的接口。

报告建议将现状写入设计文档“已知限制”，与 README 的设计文档不得记录现状差距规则不符：限制应留在本审计/阶段记录，设计文档仅写采纳后的行为。OURS_NEWER 也不能简单承诺让旧代码按当前结构只读消费；可安全提取的标记概要与未知业务数据的访问能力应分开设计，未经论证不新增通用只读加载功能。

### MA-05：承认计数，不建议当前落地

**类别：简化（有行为代价，建议保留现状）。** 重复扫描确有成本，但当前用户明确要求非支持类型直接拒绝，且已认可 commit 校验不可直接删去。仅按本 tick 是否调用 update 决定校验，会遗漏跨 tick 仍待修复的非法脏单元；标记如要引入，必须跨失败提交保持，set 改写别的字段不能清除整单元待验证状态。

原报告提出的只读引用违规差异还不能由现有开发抽查补足：[commit.ts](../../src/kernel/memory/commit.ts) 第 48–50 行仅抽查未标脏单元，恰好会跳过“set 后已脏、随后又绕过访问器修改”的单元。跳过脏单元校验后可能静默省略 undefined 或执行 toJSON，恢复本轮刚收紧的错误行为。因此不建议为这项计数收益改变当前拒绝保证；若未来考虑，须先单独批准信任边界变化，或给出不降低校验保证的方案与实测收益。

### 修订后的处置结论

原报告并非五项均可直接照单整改：MA-01、MA-03 是应处理的正确性/集成问题；MA-02 应作为提交策略决策，当前保留已批准契约；MA-04 延后至根 schema 升级；MA-05 暂不实施。仍建议先处理 MA-01/03 再完成模块合并验收，但不再以“已确认 3 项契约违约 P2”概括。

范围外 CORRUPT 条文问题确实需要另行澄清：无法解析的文本不能按键保留，备份也不等于遵守当前“不清空”的字面要求。此项仅保留报告，不修改受保护的 architecture，也不把备份后覆盖当作已授权操作。本轮未实施任何整改。

## MA-02 单元级隔离的整改与复核（2026-10-19）

本节独立于以上各节。用户在上一节完成后明确指示"实施单元级隔离"，即采用原报告 MA-02 的方案 B。上一节"MA-02 维持现状"的记录保留，作为当时的处置；本节记录其后的实施。仍在 `feat/kernel-memory`、HEAD `57f1290` 的未提交工作区进行，未修改 README、AGENTS、architecture，未提交、合并或部署。

### 设计决策

逐条回应评估修订中"若选择 B，应先补设计决策"列出的问题。均写入 [Memory 模块设计](../design/kernel/memory.md)，不改变架构 6.2、6.3、6.6 的约定：reset 后首次提交仍完整编码一次，`update` 仍在 commit 时校验，提交顺序不变。

| 问题 | 决策 |
| --- | --- |
| reset 后首次提交时没有编码基线 | 只有 `update` 能使单元变为非法。`update` 在单元尚无编码基线时，先编码当时已校验的数据作为基线，失败时沿用。只在 reset 或新建后的首次 `update` 多一次单元编码 |
| 新单元不落盘时的索引与空实体 | 同一规则：新单元以首次 `update` 前的合法数据为基线写出，不需要省略逻辑，不产生空记录或缺失的索引项 |
| 失败单元的标脏与重试 | 保持脏状态与待校验标记，每次提交重新校验一次；只剩被隔离单元待写、且无结构变化时不写入 |
| 尺寸、待确认文本与返回值 | 都以实际写出的候选文本为准，包含沿用的编码；返回 true 表示写入口成功，其中可能包含被隔离单元 |
| 日志刷屏 | 每个单元每次进入隔离只告警一次，报告单元身份；恢复后再次失败重新告警 |
| 混合版本快照 | 接受：持久文本中被隔离单元停在其最近合法版本，其余单元为最新版本；已在模块设计中说明 |

### 实现

- [unit.ts](../../src/kernel/memory/unit.ts)：`encoded` 改为"最近一次已知合法的编码"，新增 heap 字段 `isolated`。
- [accessor.ts](../../src/kernel/memory/accessor.ts)：`update` 在尚无基线时先编码。
- [commit.ts](../../src/kernel/memory/commit.ts)：
  - 校验失败的单元沿用 `encoded`，首次进入隔离时登记告警；
  - 告警在重入保护内发出；
  - 只剩隔离单元时返回 false、不写入；
  - 写入成功后只清除已编码单元的脏状态，并结束其隔离。
- 失败单元理应必有基线；万一缺失，说明前提被破坏，此时按原语义中止提交。
