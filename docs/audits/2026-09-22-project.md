### G01（P3）：订阅回调沿用发布者的阶段

- 位置：`src/core/framework/createFramework.ts:215`（`invoke(id, currentPhase, () => listener(data))`）、`:289`（`onDispose` 写入当前的 `activeCleanup`）。
- 机制：Framework 包装的订阅回调以订阅者身份、但以**发布者当时的阶段**执行。当插件 A 在自己的 setup 中发布事件时，订阅者 B 的回调处于 `setup` 阶段，于是：
  - `onDispose` 通过检查，但写入的是正在 setup 的 A 的清理列表；
  - B 可以在自己的 setup 之外新增订阅，也可以发布服务（只要在 `provides` 中声明）。
- 复现：B 在回调中登记清理函数，停用 A 后该清理函数被执行，而 B 仍在运行；B 在回调中新增订阅成功。
- 影响：需要在回调中调用 setup 专属接口才会触发，概率低；一旦触发，清理时机错误，并绕过"只在 setup 中订阅与发布服务"的约束。首轮审计曾把这一现象列为语义提醒（2026-09-20 §5）。
- 建议：为事件回调设立独立阶段（例如 `event`），setup 专属接口一律拒绝；另行确定回调中是否允许提交意图。

### G02（P3）：错误边界不去重持续故障

- 位置：`src/core/errorMapper/createErrorMapper.ts:56–59`（默认 `reportFailure` 每次都 `log.error`），由 Framework 的 `invoke` 调用。
- 复现：主存储损坏时连续运行 5 个 tick，MemoryManager 只记录 1 条（根因），ErrorMapper 记录 5 条。被缓存的确定性申请失败同理，直到熔断打开。
- 影响：存储损坏期间控制台每 tick 刷一条错误，不符合 Core 架构 §10 第 4 条“一次事件一次”；若装配开启邮件，每 tick 都会调用 `Game.notify`（该函数会按间隔合并，但调用本身仍在发生）。
- 建议：边界按（插件、阶段、消息）去重，只在首次出现与原因变化时报告，故障解除后重置；`PluginFailure` 的结构化记录保持每次都生成。

### G03（P3）：可选依赖的服务缓存失效

- 位置：`src/core/framework/createFramework.ts` 的启用集合计算只对 `requires` 级联挂起使用者；`optional` 的使用者不会随提供者一起释放与重新 setup。
- 复现：消费者 C 以 `optional: ['p']` 声明依赖，在 setup 中缓存 `services.get('svc')`；停用再启用 P 后，C 缓存的是 id 1 的旧实例，当前实例为 id 2。旧实例的事件订阅已在释放时取消，缓存随之不再更新。
- 影响：`requires` 依赖没有此问题；可选依赖的使用者如果在 setup 中缓存服务，会在提供者重启后静默使用失效实例。使用说明的示例恰好在 `onTickExecute` 中每次调用 `services.get`，但没有写明规则。
- 建议：文档写明“在使用时调用 `services.get`，不在 setup 中缓存可选依赖的服务”；是否让可选依赖的提供者重启时也级联重新 setup 使用者，需要决定。
- 复核补充：同批替换提供者时 `requires` 使用者同样受影响，见 §9.2。

### G04（P4）：`flag.id` 通过编译

- 位置：`src/type.d.ts:16`（`interface RoomObject extends _HasId {}`）；`@types/screeps` 中 `Flag extends RoomObject`。
- 复现：`(flag: Flag) => flag.id` 编译通过，运行时旗帜没有 `id`。
- 建议：把 `_HasId` 约束收窄到确实带 id 的对象类型，或在使用处改用更精确的类型。

### G05（P4）：Profiler 报告

- 位置：`src/core/profiler/createProfiler.ts:156–181`。
- 标题行“Profiler 报告 (共 N 项)”使用 `info`（默认关闭），数据行使用 `report`（默认开启），默认配置下只见数据行；`report(detailed)` 的 `detailed` 参数只是占位，契约注释也写明未实现。
- 建议：标题行改用 `report`；实现 `detailed` 或从契约中移除。

### G06（P4）：两种部署的 source map 不一致

- 位置：`rollup.config.mjs:62`（`copyPath` 部署原样复制 map）；`build/rollupPlugins.mjs:125`（API 上传时删除 `sourcesContent`）。
- 本地产物中 `sourcesContent` 约 179 KB。`copyPath` 部署的 map 模块因此更大，模块加载与首次错误映射的解析成本也更高。
- 建议：两条部署路径使用同一处理（统一删除 `sourcesContent`）。

### G07（P4）：EventBus 的作用域标签

- 位置：`src/core/eventBus/createBus.ts:249`（`notify` 中的 `const label = scopeLabel(scope)`）。
- 标签只用于 info 日志，但每次发布都会为房间和编组作用域生成一次模板字符串。开销很小，可在需要时再生成。

### G08（P4）：测试与文档缺口

- roomShortcuts 语句覆盖率 75.7%：大部分查询接口（`getExtension` 等）和销毁事件的校验分支没有测试。
- 控制台表单与帮助工具（`createForm`、`createHelp`）覆盖率 0%，与 A11 相关。
- roomShortcuts 基于 `FIND_STRUCTURES`，查询结果包含非己方建筑（例如有视野的他人房间中的 spawn）；设计文档没有说明这一语义，模块也没有使用说明。
