# Screeps Leviathan

Screeps Leviathan 是一个使用 TypeScript 开发、能长期无人值守运营的 Screeps AI。

**当前状态**：工程已初始化，构建、类型检查、单元测试与部署工具链已建立；私服场景测试待建立。开发阶段与里程碑见[设计文档](./docs/design/README.md)。

## 开发命令

环境要求：Node.js 24 及以上、npm 12 及以上，以 `package.json` 的 `engines` 为准。

```bash
npm ci                # 安装依赖
npm run typecheck     # 类型检查（游戏代码与测试代码分别检查）
npm test              # 单元测试
npm run build         # 构建 dist/main.js 与 source map
npm run check         # 依次运行以上三项
```

命令以 `package.json` 的 `scripts` 为准。私服场景测试命令建立后在本节补充。

### 部署

部署凭据保存在不会提交到仓库的 `.secret.json` 中，以账户名为键，可以配置多个账户，格式见只含占位值的 `.secret.json.example`。部署工具不设默认账户：除 `accounts` 外，每条命令都必须用 `--account` 指定目标账户。

```bash
npm run deploy -- accounts                                    # 列出已配置的账户与服务器（不显示令牌）
npm run deploy -- branches --account <账户>                   # 列出该账户的代码分支与生效分支
npm run deploy -- upload   --account <账户> [--branch <分支>]  # 构建、上传并回读校验
npm run deploy -- upload   --account <账户> --activate         # 上传后把生效分支切换到该分支
npm run deploy -- activate --account <账户> --branch <分支>    # 切换生效分支
npm run deploy -- rollback --account <账户>                   # 把生效分支切回上一个版本分支
```

- 未指定 `--branch` 时上传到版本分支 `v<版本号>`。版本分支是回滚的依据，只能在工作区干净且 HEAD 带同名标签（即 `master` 上的发布提交）时上传；开发调试用 `--branch` 指定其他分支名。
- 覆盖当前生效分支会立即改变线上运行的代码，只在同时给出 `--activate` 时允许。
- 上传、切换生效分支与回滚都是外部操作，需单独发起（见[验证与发布](#validation)）。

<a id="development"></a>
## 项目开发规范

本节适用于整个仓库的所有开发者，包括参与开发的 agents。语言、代码、文档、验证、发布与 Git 的流程要求以本节为统一入口；agent 的任务范围、协作与交付行为由 [AGENTS.md](./AGENTS.md) 补充。项目说明性文档统一放在 `docs/`，根目录只保留本文件与 `AGENTS.md`。

架构约束，包括目录结构、分层与依赖边界、持久化边界、资产控制与代码范式，统一以[设计文档](./docs/design/README.md)为准，本文件不重复定义。设计和实现须考虑每 tick 的 CPU、global heap、Memory 编解码成本、跨 tick 一致性与 global reset 恢复。

<a id="language"></a>
### 语言约定

文档、源码注释、提交信息、审计与评审报告使用简体中文；代码标识符、文件与目录名、分支名使用英文。引用代码、命令、API 名称与配置项时保持原文。

<a id="source-comments"></a>
### 源码注释

`src/` 下所有源文件都应有清晰、详细且与实现同步的注释，使后续开发者能理解设计理由、运行机制和维护边界。

每个源文件在 import 之前写文件摘要；若语言工具要求指令位于首行，摘要紧随该指令。摘要至少说明文件解决的问题及职责、所属模块及位置、主要输入输出或对外能力，以及重要状态、缓存、外部依赖或运行时副作用。

依据实际复杂度，注释还应解释以下适用事项：

- 方案选择、算法原理、执行顺序、复杂度及性能取舍；
- 关键实现细节、边界条件、失败路径、降级行为和维护约束；
- 非直观的 TypeScript 类型技巧、类型收窄或 JavaScript/TypeScript 语法；
- 关键变量、状态容器、缓存、计数器及版本字段的作用和生命周期；
- 第三方包的用途、调用约定，以及所依赖的具体行为；
- Screeps API 的运行时限制、CPU 或 Memory 成本及跨 tick 影响；
- 其他有助于理解、测试、排错和后续修改的非直观信息。

**方法注释遵循 JSDoc。** `src/`、`scripts/` 及测试辅助模块中所有具名函数与方法（含导出的箭头函数、对象字面量方法、类方法，以及接口与类型中的方法签名）都要写 JSDoc 块注释；传给 `map`、`test` 等的内联匿名回调除外。

- **必备字段**：
  - `@description`：方法的职责与关键行为；
  - `@param`：每个参数一条，名称与签名一致，说明含义、取值约束与默认值；对象参数用 `@param opts.字段` 逐项说明；
  - `@returns`：返回值的含义；无返回值时写明"无返回值"，并说明产生的副作用。
- **复杂方法补充字段**：会抛错、带泛型、修改状态或存在非直观调用约定的方法，按需补充，使读者不读实现也能正确调用：
  - `@throws`：每类异常及其触发条件；
  - `@template`：泛型参数的含义与约束；
  - `@example`：调用方式不直观时给出示例；
  - `@see`：对应的设计文档或架构章节。

定义 Map 变量时，在定义旁的注释中明确写出 key 与 value 的具体含义，采用类似 `{ [key含义]: value含义 }` 的映射形式。复合 key 必须说明组成字段、顺序与分隔符；value 为 Set、数组或嵌套 Map 时，继续说明集合元素或内层 key/value 的含义，不能只重复 `string`、`Set<string>` 等类型。实例状态和函数内临时 Map 均遵守此规则。

注释解释"为什么"和"如何工作"，不逐句复述代码。新增或修改源文件时，使涉及的文件满足本节。

<a id="implementation-state"></a>
### 实现与状态

代码写法遵循设计文档的代码范式。

**模块引用**：`@/` 是 `src/` 的别名（`tsconfig.json` 的 `paths`）。跨模块导入一律写成 `@/<路径>`，不使用相对路径；相对路径只用于同一模块内部的文件之间。测试代码引用 `src/` 时同样使用 `@/`。模块的划分如下，由边界测试检查：

- `src/` 根目录的文件各自为一个模块；
- `contracts/` 整体为一个模块；
- 领域模块为 `domains/<分组>/<领域>/`；
- 其余为 `<层>/<模块>/`，层目录下的单个文件以文件名为模块。

单个文件的有效内容（不计空行和纯注释行）如非必要不超过 300 行。这是建议项，不作为阻断条件：超出时优先按职责拆分，确有必要保持在同一文件时可以保留。

有明确的 Screeps 性能收益时，可以在模块内部受控地原地更新，或用闭包保存缓存、索引、状态和预计算结果。此时须在注释中交代状态的创建位置、命中与更新方式、失效与清理条件、跨 tick 有效性、global reset 后行为，以及性能收益和一致性风险。

Logger 只承载纯文本日志，作用域名和正文在统一出口转义；调用方传原文，不向日志传入 HTML 片段。富文本运维交互由独立模块提供，不能借 Logger 输出。

<a id="module-docs"></a>
### 文档规范

`docs/` 分为三部分，各部分的命名与维护规则见其索引：

| 部分 | 位置 | 用途 |
| --- | --- | --- |
| 设计 | `docs/design/` | 设计意图：总体架构、模块设计、运维手册；模块设计文档的位置与 `src/` 的目录一一对应 |
| 提案 | `docs/proposal/` | 设计变更的论证与决策记录 |
| 审计 | `docs/audit/` | 审计报告与里程碑审查，包括已完成的变更与验证结果 |

通用规则：

- 设计文档只写设计意图，不写项目现状盘点、现状与目标对照、重构前后差异或既有代码与设计的差距分析。
- 设计文档面向第三方读者，写成客观、结论性的文字，着重设计思路、架构与关键细节；不引用其他项目作为依据，不记录讨论过程。平台事实注明依据：公开源码或官方文档。
- 新增设计内容放在相关章节旁，而不是追加到文末；章节编号变动时，同步修正全部交叉引用，并核对每个引用指向的内容而不只是编号存在。
- 设计变更先写提案，采纳后再更新设计文档；提案保留原始论证。
- 修改模块的公共行为、配置或返回契约时，同步更新对应的设计文档。
- 阶段性更新记录在里程碑审查中，不写进设计文档。
- 源码目录新增、移动或更名时，同步移动对应的设计文档。
- 文档新增、移动或更名时，同步更新所在部分的索引与所有引用，包括源码注释中的路径。只链接已经存在的文档。
- 历史提案与审计记录按当时的日期、基线和验证范围阅读，不覆盖为当前状态。命令与 API 说明核对相应配置、契约和实现后更新。

<a id="audit-reports"></a>
### 审计报告

审计报告中的每项问题必须提供可复查的定位与影响依据：

- 能定位到代码时，写明仓库相对文件路径、审计基线下的具体行号及函数、类型或分支名称，并提供文件链接。涉及跨模块调用或生命周期时，分别列出问题来源、传播路径与影响落点，不能只指向整个目录或模块。
- 无法归结到具体代码位置时，明确说明原因（例如缺失的实现、跨模块协议缺口或外部运行条件），并写清触发条件、状态或数据如何传播、最终影响哪些行为及影响边界；能定位的相关入口和契约仍须列出。不得以"可能有风险"等笼统结论代替影响机制。
- 文档、配置和构建问题定位到相应文件的行号、章节或配置项，不编造源码位置。报告标明代码基线；后续修订区分原审计记录与复核结果，行号须能与所述基线对应。
- 区分源码确认、测试复现和待验证推断，给出各自证据及未覆盖范围。有限 tick 的复现不能直接推导永久故障，平台替身测试不能写成真实引擎验证。

<a id="validation"></a>
### 验证与发布

完成代码或构建系统修改后，按顺序运行与变更相符的检查：类型检查、单元与边界测试、构建；涉及引擎行为、跨 tick 状态或运营闭环的变更，再运行相应的私服场景测试；最后运行 `git diff --check`。对应的命令为 `npm run typecheck`、`npm test`、`npm run build`（或合并为 `npm run check`）与 `git diff --check`；私服场景测试为 `npm run test:scenarios`（需要 Docker，`-- --only <场景名>` 只运行单个场景）。

纯文档修改至少检查差异空白，并核对改动文档的链接与章节引用。交付说明应列明未通过或未运行的检查、原因和影响。

构建必须在没有 `.secret.json` 时也能成功；构建与验证不得隐式上传。上传代码、切换官服生效分支与执行线上运维命令都是外部操作，需单独发起，发布流程以设计文档为准。

<a id="git-workflow"></a>
### Git 分支与版本

**分支：**

| 分支 | 用途 | 来源与去向 |
| --- | --- | --- |
| `master` | 发布分支，每个提交都是可部署的版本；部署到官方服务器只使用 `master` 上带标签的版本 | 只接收来自 `dev` 的发布合并与紧急修复 |
| `dev` | 日常集成分支，保持可构建、测试通过 | 接收任务分支的合并；发布时合并到 `master` |
| `<类型>/<主题>` | 任务分支，类型取 `feat`、`fix`、`docs`、`refactor`、`test`、`chore` | 从 `dev` 拉出，验证通过后合并回 `dev` |
| `hotfix/<主题>` | 线上紧急修复 | 从 `master` 拉出，修复后合并到 `master` 并同步合并回 `dev` |

- 合并使用 `--no-ff`，保留任务的提交边界；合并后保留分支。
- 合并到 `master` 时打标签 `v<版本号>`。标签对应的版本就是线上版本与回滚目标。

**版本号：**

版本号为 `a.b.c`，记录在 `package.json` 的 `version` 中，初始版本为 `0.1.0`。

| 部分 | 何时变化 |
| --- | --- |
| `a` | 全部里程碑完成前为 0；全部完成后为 1；之后只在持久化数据或运维方式出现不兼容变更时加 1 |
| `b` | 取当前里程碑的编号；进入下一个里程碑时加 1，`c` 归零 |
| `c` | 每个改变构建产物的任务合并进 `dev` 时加 1；紧急修复取 `dev` 与 `master` 中最大的 `c` 再加 1 |

- **何时改版本号**：只在合并提交中修改。任务分支上的普通提交、发布到 `master` 的合并、不改变构建产物的合并（例如只改文档或测试）都不改版本号。发布到 `master` 时直接为当前版本打标签。
- **构建产物**：`src/`、构建配置（`rollup.config.mjs`、`tsconfig.json`）与 `package.json` 中的依赖声明发生变化，即视为改变了构建产物。
- **工具**：`npm run version:bump [task|milestone|hotfix]` 按规则写入下一个版本号（默认 `task`）；`npm run check:version` 校验工作区中的版本号是否符合规则。

合并任务分支到 `dev` 的步骤：

```bash
git switch dev
git merge --no-ff --no-commit <任务分支>
npm run version:bump        # 改变了构建产物时执行
npm run check:version
git add package.json package-lock.json
git commit
```

<a id="secrets"></a>
### 密钥与敏感信息

不得提交 `.secret.json`、认证令牌、账号凭据或包含真实凭据的命令输出。公开配置示例只使用占位值；报告、测试夹具和文档也不得泄露真实凭据。
